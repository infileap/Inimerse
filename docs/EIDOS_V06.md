## 1. 归档设计的下落

### 1.1 已经裁定过、而归档文档不知道的

**【已裁】Eidos 变成「内糖」—— 编译器认识它，VM 不需要。**

用人类本人的词（`U195`）：**内糖 = 可直跑；外糖 = 需脱糖**。

- **编译器侧认识 Eidos**：声明、成员、继承、`super`、字段引用由**编译器**解析并**检查** —— 尤其「开放与封闭」（可见性、可继承性、可覆写性）**在编译期判定**。
- **VM 不需要认识它**：编译器把它降到引擎已有的构造（今天的脱糖器做的就是这件事）⇒ **不新增 opcode、不新增运行时类型信息**。
- **被否掉的两条**：① **保持外糖**（「开放与封闭」只能在脱糖期**擦掉**、不能在编译期**守住**）；② **完整内建**（会让 Eidos 成为 VM 的一个新决定点，与去 C 化的方向直接对撞）。

### 1.2 今天的读数

- `src/`、`mods/`、`selfhost/`、`vtest/` **四个目录里 Eidos 零字节**。
- 脱糖器（`tools/eidos_desugar.py`，516 行）的产物**只用了引擎已有的构造**（`func`、字典字面量、闭包、`??`、`record`）。
- 关键字表里有 `record`/`recorded`，**没有 `eidos`/`ed`**。
- **它明确拒绝 Mixin**：脱糖器有一条错误串逐字 `Eidos mixins are not supported by the v0.4 desugar subset`。

★ **解释（不是事实）**：**「零字节不是决定，零字节是零字节」** —— 它同样可以是「停在这儿了」或「还没轮到」，而这三者在今天的树上长得一模一样。**一个形状要被读成裁决，得有人写下它。**

### 1.3 ★ 归档里的 Mixin 与本文的 `@unfold` 是同一件事的两种拼写

归档 §2.5「继承」逐字给出：

```
eidos Dragon: Monster + Flying {   # 多重继承（Mixin）
```

并给出三条规则：**单继承用 `:`，多重继承（Mixin）用 `+`**、**方法查找从左到右，子类优先**、**`super` 调用最近的父类实现**。

★★ **这与人类新提的 `@unfold eidos extend animal, pet` 是同一件事的两种拼写。**

★★ **【已裁】保留 `@unfold eidos extend A, B`；归档的 `eidos C: A + B` 作为一种【记录】留在归档原文里，不进入现行语法。**

★ **理由**：`+` 只能表达「从谁那里取」，**不能表达「取哪一个成员」**；而 §3.2 的歧义诊断需要点名来源（`keep one: bark from animal`），**`+` 拼写里没有那个名字的位置。** ★ **代价是**：归档 §2.5 与 `future/archive/Inim OS总纲.md` 的两处表格仍写着 `+` —— ★ **它们是【记录】不是【指针】**，不改原文（见 §10 ⑤）。

★ **边界**：本条只裁【拼写】。★ **「方法查找从左到右，子类优先」这条顺序语义没有跟着作废** —— 它在 `@unfold extend A, B` 里就是「`A` 在左、`B` 在右」；而 §4 已经裁的是 `super` 怎么指名，**不是这个顺序**。

★★★ **而更要紧的是那第三条规则**：**「`super` 调用最近的父类实现」就是位置式 `super`** —— 正是本文 §4 建议要改掉的那一条。**归档在这一点上与新提案直接冲突，而这不是笔误，是一个设计选择。**

### 1.4 归档里今天仍然成立、且是本文前提的部分

| 节 | 内容 | 为什么它仍然成立 |
|---|---|---|
| §2.1 | Eidos 定义 | 与脱糖器一致 |

### 1.5 ★ `invariant` 是唯一一条与「VM 不需要认识它」有张力的

归档 §4.5 逐字：**「每次属性修改后自动检查不变量，违反时触发 `on_violation`。」**

- 另外四条封闭手段（可见性、`final`、`sealed`、`frozen`）**都在编译期判定** ⇒ 与裁定严丝合缝。
- **`invariant` 不是**：它要求**每一次属性写入之后**执行一段用户代码。★ 这有两条实现路：
  - **(a) 编译器把它降到已有的构造**（在每次赋值后插入一次调用 + 一个失败分支）⇒ **VM 仍然不需要认识 Eidos** ✓ 与裁定一致。
  - **(b) VM 认识 `invariant`** ⇒ 与裁定冲突。

⇒ **【已裁】走 (a)。** 而它有一个必须写下来的代价：★ **它把「每次属性写入」变成一个语义上非平凡的位置** —— 编译器必须在**所有**写入点（含容器元素、含 `frozen` 之外的路径）插入检查，**漏一个就是一个静默失效的不变量**。★ **这条的验收见 §9.5。**

★★★ **【已裁】语义是【违反时调 `on_violation`】—— 修复，不是【拒绝写入】。** 人类在 `ask_user_question` 上选的，而实测把它的语义也定死了：

1. ★★ **JS trap：`p.exp = 500` 被拒之后，对象状态是 `exp = 500`** —— ★ **写入已经落地** ⇒ ★ **「先写后查」拦不住那次写入** ⇒ ★ **「拒绝写入」这条语义在 (a) 的实现里不存在。**
2. ★ **而归档 §4.5 本来写的就是事后语义**（它的例子 `level += 1; exp = 0` **是在修复**）⇒ ★ **「拒绝」是我读出来的，不是它写的。**

★★ **两条必须一起写下的代价 / 边界**：★ **(i) 容器元素写入绕过检查是【写下的边界】，不是缺陷**（Python 实测同形：`b.items = [1, 999]` 里 append 一次都没触发钩子）；★ **(ii) 不提供关闭它的构建开关** —— ★ **实测 C 的 `-DNDEBUG` 会让断言整个消失（`跑过了, level = -5`），Rust 的 `assert!` 不会但 `-C debug-assertions=off` 会** ⇒ ★ **同一个语言两档都提供、而哪一档是默认可选** ⇒ ★ **Eidos 必须明确禁止那一档，否则不变量会在某次构建配置里静默消失。**

## 2. 两个标记的形状

**人类给出的形状（拼写已按 §6.1 的裁定改为 `@mixin`）：**

```
@mixin eidos animal {
    bark {}
}
@mixin eidos pet {
    bark {}
    play {}
}
@unfold eidos extend animal, pet {
    play { super }
}
```

展开为：

```
eidos cat {
    bark {}
    play {}
}
```

### 2.1 `@mixin`（初稿拼写 `@template`，见 §6.1 的裁定）

**声明一个 mixin：不能创建实际对象。**

★ **它必须能非零地回答两个问题，而这两个问题今天的提案里没有写**：

1. **mixin 能出现在类型位置上吗？** `f(x: animal)` —— 而 `animal` 不是任何对象的类型。
2. **mixin 能被别的 mixin `extend` 吗？** `@mixin eidos c extend a, b` —— ★ 若能，则 `@mixin` 与 `@unfold` 的组合有无限多种，**环检测（§7.3）就是必需的而不是可选的**。

### 2.2 `@unfold`

**标记一个类或宏，在编译前展开（如同外糖）。**

★ **「如同外糖」这句话与 §1.1 的裁定有张力**，而它需要被说清：★ **外糖的意思是「展开发生在编译器之前」，而裁定的意思是「编译器认识它」。** 两者可以同时成立，**但只在一种写法下**：

> **编译器做展开，而不是外部工具做展开。** 展开的**语义**由编译器负责（所以它认识 Eidos 的封闭规则）；展开的**结果**是一份编译器内部的东西（所以它不需要 VM 认识）。

⇒ **【提案】`@unfold` 由编译器执行，不是 `tools/` 里的一个脚本。** ★ 否则封闭规则（`final`/`sealed`/`frozen`）永远只能在展开期**擦掉**，而这正是被否掉的那条路。

## 3. 合并规则

**这是整个设计的重心。** 三条规则里，第一条需要重写，第二条需要一句现在还没有的话，第三条需要一个现在还没做的选择。

### 3.1 ★★★ 第一条：同名且相同 ⇒ 只保留一份

**人类给的规则**：「如果两个同名方法相同（如这里的 `bark{}`），只保留一份」。

★★★ **问题：「相同」把「两个函数体的相等」变成了一个语义原语，而文本相同不是语义相同。** 真正的后果是：

> 今天 `animal.bark` 与 `pet.bark` 文本一样 ⇒ 合并成一份。
> 明天有人改了 `animal.bark` 的一个字 ⇒ **`cat` 变了，而没有人编辑过 `cat`。**

★ **这比通常的「脆基类问题」更坏一层**：正常继承里，改基类影响子类是**预期内**的；而这里，**同一次编辑可能改变 `cat`、也可能不改变 `cat`**，判据是**一个从来没有人写下来的性质**。

★★★ **这种耦合没有任何读数能看见它** —— 它不是「一个数没印出来」，是**「这条边存不存在」本身没印出来**。

**三条可选路：**

- **(a) 纯静默合并**（初稿提案写的）—— 简单，但上面那个洞永远在。
- **(b) 相同也必须显式**：写 `bark from animal`，文本一样也不自动合。
- ★ **(c) 静默合并，但【必须报出来】，且这个报告本身可被钉住。**

★★ **【已裁】(c)。** 人类在 `ask_user_question` 上选的是它；下面补上它的边界。

**(c) 的形状**：编译器输出一行 `merged: animal.bark == pet.bark (identical bodies)`，**并允许把这一行钉成一条断言** ⇒ **哪天它们不再相同，那条钉会红，而红的地方正是当初做合并决定的地方。**

★ **理由（与本仓库已有的家法一致）**：**值 + 守卫 = 安全；值 + 无守卫 = 病。** 合并是一个值，而它在 (a) 里**没有守卫**。

★★ **边界（这一条必须写下来，否则 (c) 会被读成 (a) 加一句输出）**：★ **(c) 与 (a) 的可区分性完全落在【那行报告被钉住了没有】。** 若没有钉，**(c) 在行为上与 (a) 相同** —— 差别只剩一行没人读的 stdout。⇒ ★ **「可钉住」不是修辞，它是这条裁定唯一的载荷**；它的验收见 §9.1。

### 3.2 ★★ 第二条：同名而不同 ⇒ 必须覆写

**规则本身对。** 但它把**一个歧义**呈现成了**一个命令**。作者看到的会是一句「你必须覆写 `bark`」，然后他写一个 `bark{}` —— ★ **而这一覆写同时丢掉了 `animal.bark` 与 `pet.bark` 两份实现，且没有任何东西告诉他丢的是哪两份。**

**【提案】诊断必须点名来源，并给出「只取一份」的写法：**

```
error: `bark` comes from `animal` and `pet` with different bodies
  → override it here (discards both), or
    keep one:  bark from animal
```

★ 理由：**「另一条路是什么」必须写出来，否则读者以为只有一条路。**

★★★ **【已裁】诊断的形状照 `rustc --error-format=json` —— 它是一个树，而且比本节的草案多两样。** 人类在 `ask_user_question` 上选的。逐条实测（本机 `rustc 1.99.0`）：

- ★ **每个来源是【带 `span` 的 child】**，不是文本里的一句：`spans[]` 带 `is_primary` / `file_name` / `line_start` / `text` / `label`；★ **`children[]` 各带自己的 `spans[]`**。
- ★★ **每个「可选写法」是【带把握度】的 fix**：`suggested_replacement` + **`suggestion_applicability`**，而后者**是一个两档以上的枚举** —— ★ 歧义消解给 `HasPlaceholders`（**还有占位符没填**），拼错方法名给 `MaybeIncorrect`。⇒ ★ **一个 fix 必须携带「它有多大把握」。**
- ★ **`g++ -fdiagnostics-format=json` 也是树**（`kind` / `message` + `children[]`）；★ **而 `clang++ -fdiagnostics-format=sarif` 是扁平的 `results[]`，父子关系丢失**（只剩顺序）⇒ ★ **同一件事有三个真编译器作答，而其中一个是错的形状。**

★★★ **而「照抄一个现成形状」这条裁定有一处边界，它是与四个真实现并排之后才看见的**（逐字段对照见下）：

1. ★★★ **本节的核心要求 —— 「点名来源」—— 在四个实现里【一个字段都不是】。** ★ 它只活在两种地方：**散文**（`candidates are: ‘int Y::hp’`）或 **fix 的替换串**（`A::f(&s)`）。★ **而唯一带「把握度」的 fix 字段（`suggestion_applicability`）只有 rustc 有** ⇒ ★ **「机器可读地点名来源」这件事，没有现成形状可抄，必须自己设计。**
2. ★★ **「字段清单」不是一个全局 schema，是【按诊断种类变的】** —— ★ rustc 的 `code` 在三条诊断里 **2 条是 `null`**、`spans` **2 条是空**；gcc 的 `option` / `option_url` **只出现在 `warning` 上**（**它的 error 条目根本没有 fix 字段**）⇒ ★ **一份字段清单如果不写「在哪一类诊断上」，它列的是并集，而并集在每一行上都不成立。**
3. ★★★ **位置的单位不定，位置本身就不是可核的** —— ★ **三家都处理了「第 27 列」的歧义**：clang 显式给 `columnKind: unicodeCodePoints`、gcc 给 `byte-column` 与 `display-column` 两列、rustc 给 `column_start` + `byte_start`。★ **而本节要的「点名来源」正建立在位置上。**

### 3.3 ★★★ 第三条：参数不同不算同名 —— 而「保证不存在重叠」有两个相反的答案

**人类给的规则**：「名称相同但参数不同的不视为同名方法（`run a:float` / `run a:int` / `run{}` 三个不同），但编译器必须通过集合关系保证不存在参数重叠」。

★ **「保证不存在重叠」是【不相交】方案。而人类举的例子里那个 `run{}` 恰好是它排除掉的东西** —— 零参签名是**兜底**，而兜底与特化**必然重叠**。

| | **不相交**（初稿提案写的） | **最特化优先**【已裁】 |
|---|---|---|
| 规则 | 任意两个签名不得相交 | 允许相交，**更特化的赢**；只有**互不更特化**才算歧义 |
| `run a:int` + `run a:Z` | **非法** | 合法，传 `int` 走 `int` 那支 |
| `run{}` 兜底 | **与所有签名冲突 ⇒ 写不出来** | 合法，兜底最不特化 |
| 要证的义务 | **所有两两配对都不相交** | **只有实际相交的那几对要能分出胜负** |
| 判据的难度 | 集合表达式的一般相交判定（算子一多就很难，甚至不可判定） | 只比较两个签名，**可判定** |

★★ **【已裁】取「最特化优先」。** 人类在 `ask_user_question` 上选的是它，三条独立的理由：

1. **人类自己举的 `run{}` 只有在最特化优先下才有意义。**
2. **证明义务要尽量小**：不相交是对**所有配对**的证明；最特化只对**真正重叠的配对**证明。★ 而这是一个**集合式类型系统** —— 集合表达式上的相交判定会随算子增长而变贵。
3. **不相交会把「我想给 `int` 一个特例、其余走通用」这条最常见的需求变成写不出来。**

★ **边界**：① **不相交没有被证伪，它只是没有被选** —— ★ **本条裁的是「允许相交、更特化的赢」，不是「集合相交判定不存在」**；② ★★ **最特化优先把证明义务从「所有配对」缩到「真正重叠的配对」，而那几对仍然要能分出胜负** —— **判不出来就是歧义，必须报错**，不是随便挑一个。

★★ **还有第三条路（本轮未取，记在这里因为它最像这个仓库的脾气）**：**编译器不判「有没有重叠」，它报出【重叠的那块类型】** —— 「`run a:int` 与 `run a:Z` 在 `int` 上重叠」。★ **是报，不是拒。** 这与本仓库反复出现的形状一致（**记录 vs 指针**、**一个零要能被归因**）。★ **它与 (A) 不冲突**：最特化优先要判的是「能不能分出胜负」，而报出重叠类型是**在分不出胜负时**给的那条诊断 —— ★ **两者可以同时存在**，只是 (A) 已经先定了「能分出胜负时不报」。

### 3.4 ★ 字段的合并规则与方法不同 —— 已裁：与 §3.1 同形

方法「相同就合、不同就覆写」。★ **字段「同名不同默认值」不是覆写，是一个没有自然解的冲突** —— 取哪个默认值？

★★★ **【已裁】字段与 §3.1 的方法走同一条规则：静默合并（两个字段都保留）+ 合并点报出 + 可钉住；而【无限定访问命中两个以上 = 编译错误】，不是静默取一个。** 人类在 `ask_user_question` 上选的。

★ **理由：同一个合并问题问两次（方法一次、字段一次），如果两次的答案不同，那么两次里必有一次是随手写的。**

★★ **实测材料（本机 `g++ 15.2.0` / `python3 3.14.4` / `node v24.20.0`）—— 三种有可比性的做法里，没有一种在合并点报错**：

| | 做法 | 后果 |
|---|---|---|
| **C++** | ★ **两个字段都保留，只拒绝无限定访问**（`error: request for member 'hp' is ambiguous` + 两条 `note: candidates are`）；★ 限定之后 `Z::hp` / `Y::hp` 都能取到 | ★ **这就是「静默合并 + 必须报出」** —— 与已裁的 §3.1 同形 |
| **Python** | **静默取第一个**（`Z.hp = 10`），换父顺序 ⇒ `Z2.hp = 20` | ★ 顺序决定结果，且**不报出** |
| **JS** | **静默取最后一个**（`new C().hp = 20`） | ★ 同上，方向相反 |
| **Rust** | 结构体字段不能来自 trait | ★ **无此问题** |

★ **诊断形状（草案那一版保留，它仍然是对的，只是不再是唯一一条路）**：报错时把两个默认值都印出来，**并且必须给出「保留哪一个」的写法**：

```
error: field `hp` has different defaults: `animal.hp = 10`, `pet.hp = 20`
  → restate it here with one value, or qualify the access to pick one
```

★ **边界**：★ **本条与 §3.3 的「最特化优先」不冲突** —— §3.3 管的是**同名方法的重载**，本条管的是**同名字段的合并**；★ **两者都不是「静默挑一个」。**

## 4. ★ `super` 必须限定 —— 已裁

**人类给的例子里 `play { super }` 里的 `super` 指向谁？** ★ 这个例子里 `play` 只在 `pet` 里，所以无歧义；**但规则必须现在写**，因为一旦两个父都有 `play`，位置式 `super` 就是多重继承里最难推理的那一部分。

★ **而归档 §2.5 已经把位置式写成了规范**：「`super` 调用最近的父类实现」。

★★ **【已裁】`super` 必须带名字** —— `super pet.play`（或 `super(pet)`）。★ 人类在 `ask_user_question` 上选的是它。

★ 理由：**这个语言的全部卖点是「编译期可判定」，而位置式 `super` 把这个卖点直接交出去** —— 它让「这段代码调用的是哪个实现」取决于**父列表的顺序**，而那个顺序在展开之后**看不见了**（§5）。

★★ **边界（三条，必须写下来）**：
① ★ **本条作废的是归档 §2.5 的第三条规则（位置式 `super`），不是第一条（`:` 与 `+`）也不是第二条（方法查找从左到右）** —— ★ **`super` 指名与成员查找顺序是两件事**：前者被这条裁掉了，后者仍然有效（见 §1.3 的边界）。
② ★★ **它是本文里唯一一条【推翻归档已经写下的规范】的裁定** —— §3.1/§3.3/§6.1 三条裁的是**新提案内部**的选择，而这一条**与归档原文直接冲突**。⇒ ★ **归档原文不改**（它是【记录】），★ **但「Eidos 的位置式 `super`」这句话从此在现行语法里不成立** —— ★ **将来读归档的人必须能在这里找到这句话。**
③ ★ **本条只裁【怎么指名】，不裁【能不能调用祖父】** —— `super` 是否可传递（`super pet.play` 里 `pet` 自己的 `super` 指向谁）**本文未判**，见 §7.4。

## 5. ★★ 展开必须带出处

**人类给的规则**：`@unfold` **在编译前展开，如同外糖**。★ 那么**编译器看到的是展开后的东西** —— **于是「`cat` 的第 3 行」这类报错会指向生成物。**

★★ **这是宏系统最经典的问题，而它有一个便宜的解法**：**展开产物必须带源位置映射**（哪个成员来自哪个模板的哪一行）。

★ **顺带它也解决了 `reflect`** —— 人类之前要过 `reflect` 标签，而「这个方法来自 `pet`」正是它该报的东西。

★★★ **一条原则**：**展开是【指针】（这个类今天长什么样），出处是【记录】（它从哪来）。两个都要，而且它们不是同一个东西。**

- **只留展开结果** = 丢掉了记录 ⇒ 报错指不到源，`reflect` 说不出出处，合并决定不可审计。
- **只留出处** = 每次都要重算 ⇒ 而这正是「编译期展平」要避免的。

## 6. 命名

### 6.1 `@template` 这个名字会被读错 —— 已改名 `@mixin`

在几乎所有语言里 `template` 意思是**泛型**（C++ templates、Java generics）。★ 而这里它意思是**抽象 mixin**。

★★ **【已裁】改名 `@mixin`。** 人类在 `ask_user_question` 上选的是它。★ 理由：**将来真的想要泛型时，`@template` 已经被占了。**

★ **边界**：① **`@trait` / `@abstract` 没有被否，它们只是没有被选** —— ★ **本条裁的是「不再叫 `@template`」，不是「必须叫 `@mixin`」**；② **改名窗口在第一个 `.im` 文件写下这个标记之前是零成本的**，之后每一次改名都是一次迁移；③ **`@unfold` 的名字没动**（它读起来就是「展开」，与 `extend` 连用无歧义）；④ ★ **归档里的 `Mixin` 一词与本标记同义** —— **这是本文第一次让归档用词与现行拼写对齐**（见 §1.3）。

### 6.2 与归档的拼写冲突 —— 已裁

见 §1.3：**`@unfold eidos extend A, B` 与 `eidos C: A + B` 是同一件事的两种拼写。**

★★ **【已裁】保留 `@unfold eidos extend A, B`**（与 §1.3 同一条裁定）。★ **归档的 `+` 拼写不进入现行语法，作为【记录】留在归档原文里。**

## 7. 尚未写的三件（一旦落地就会被问到）

### 7.1 字段怎么合 —— 见 §3.4

### 7.2 `@unfold` 可传递吗？—— 已裁：可传递，且链必须【拼接】而不是【拷贝】

**`@unfold` 的结果是模板还是类？** ★ **能再展开就定义链，不能就定义深度 1。**

★★★ **【已裁】可传递。** 人类在 `ask_user_question` 上选的，两条独立的理由：

1. ★★ **实现形态上只有一种选法**：★ **JS 实测** —— **同一个 mixin，写成 class 工厂能 `super`，写成普通对象再 `Object.assign` 进去就永远不能** ⇒ ★ **`@unfold` 若被实现成「把成员拷进目标类」，`super` 没有落脚点；必须是「把链拼成一条链」。** ★ **这不是「哪种语义更好」，是「哪种实现让 §4 的裁定有可能成立」。**
2. ★ **`super` 已经带名字（§4）** ⇒ ★ **「链上的下一个是谁」这个问题根本不出现** ⇒ ★ **不需要线性化**（Python 为它需要 C3，而 C3 无解时它**拒绝编译**：`class E(C, D)` ⇒ `TypeError: Cannot create a consistent method resolution order (MRO) for bases A, B`）。★ **Eidos 因为 §4 带了名字，连需要拒绝的机会都少了。**

★ **边界**：① ★ **「两条展开路径到达同一个祖先」不是这一条的问题，是成员解析的问题** —— 归 §3.4；② ★ **本条与 §7.4 的实测材料取自本机**（`python3` / `node` / `g++` / `rustc`），★ **而它同时是一个【由可用性决定的样本】** —— D / Eiffel / Ada 在本机核不了。

### 7.3 循环展开检测

`A` 展开需要 `B`，`B` 需要 `A`。★ **必须有环检测，且报出那个环**（不是「深度超限」）。

★ 理由：**「深度超限」是一个关于实现的读数，「这是一个环」是一个关于设计的读数** —— 前者让作者去调一个上限，后者让他去改结构。

### 7.4 ★ `super` 能不能调用祖父（§4 边界③）—— 已裁：能，因为 `super` 带名字

★ §4 裁的是**怎么指名**（`super pet.play`），**不是**「`pet` 自己的 `super` 指向谁」。⇒ **若 `pet` 也 `extend` 了 `animal`，`pet.play` 内部再写 `super` 时指向谁？**

★★ **这与 §7.2 是同一个问题**（`@unfold` 可传递吗）：**展开的深度是 1 还是一条链。** ⇒ ★ **两个问题必须一起裁，否则会出现「展开是链、而 `super` 只能走一层」这种半传递状态** —— ★ **而那个状态在今天的提案里没有任何东西会拒绝它。**

★★★ **【已裁】能调用祖父，而它【不需要线性化】。** ★ 因为 `super` 的宾语是**一个名字**（`super pet.play`），不是**一个位置**。★ **名字指哪个祖先由名字定，不由「链上的下一个」定** ⇒ ★ **§7.2 与 §7.4 一起裁的结果是：链存在（可传递），而走链靠名字（不需要顺序算法）。**

★ **对照（C++ / Rust 那一侧）**：★ 它们选的是**不可传递** —— `d.A::f()` 里的 `A` 也是写出来的名字，**而 `A` 的 `A` 不在任何链上**（Rust 的 trait 里 `super` 直接报错：`error[E0433]: too many leading 'super' keywords within 'crate'`）。★ **所以「带名字」本身不蕴含「可传递」** —— ★ **这一条裁的是「两者都要」，而它是一个独立的决定，不是前一条的推论。**

## 9. 每条规则的验收

★ **每一条规则配一个最小例子 + 一条能红的对照。** 这是本文与归档文档最大的形式差别：**归档全是陈述句，而陈述句不能红。**

### 9.1 合并（§3.1）

- **例子**：§2 那两个模板 + `@unfold`。
- **能红的对照**：★ **改 `animal.bark` 的一个字** ⇒ **那条「merged」的钉必须红**（(c) 已裁，所以这是一条必须成立的断言，不再是「若走 (c)」）。
- ★★ **而它同时是 (c) 与 (a) 的区分实验**：**把那条钉删掉、其余一个字不动 ⇒ 什么都不会红** —— ★ **这一对读数（有钉则红 / 无钉不红）才是「可钉住」这个词的载荷**；只有前一半时，(c) 与 (a) 仍然不可区分。

### 9.2 歧义诊断（§3.2）

- **能红的对照**：★ **删掉诊断里那句 `keep one: bark from animal`** ⇒ 必须有一条断言红（★ **否则「诊断会点名来源」这句话没有守卫**）。

### 9.3 参数重叠（§3.3）

- **例子**：`run{}` / `run a:int` / `run a:Z` 三者并存。
- **能红的对照**：★ **传一个 `int` 实参** ⇒ **必须走 `run a:int`**（最特化优先已裁，所以这是一条必须成立的断言）。★ **对照是把规则改回不相交** ⇒ **同一个程序必须编译不过** —— ★ **两种方案在这个例子上给出相反的可编译性，所以这条裁定的后果是可判别的。**

### 9.4 `super` 限定（§4）

- **能红的对照**：★ **交换 `extend` 里两个父的顺序** ⇒ **行为必须不变**（限定式已裁，所以这是一条必须成立的断言，不再是「若走限定式」）。★ **对照是把它改回位置式** ⇒ **同一个程序必须变** —— ★ **「顺序无关」这条性质本身，就是这个方案要买的东西，而这一对读数才是它的载荷。**
- ★ **另加一条**：★ **两个父都有 `play` 时，`super play`（不带名字）必须编译不过** —— ★ **否则「必须带名字」这句裁定没有任何守卫。**

### 9.5 `invariant` 的写入点覆盖（§1.5）

- **能红的对照**：★ **构造一个能绕过检查的写入路径**（容器元素、嵌套字段、`frozen` 之外的第二条路）⇒ 若它**能**绕过，说明写入点的枚举不全。
- ★ **这一条必须现在做**，因为它是 §1.5 那条「编译器把它降到已有构造」的**唯一验收**：★ **「每次属性修改后自动检查」里的「每次」是一个全称量词，而全称量词只能靠枚举来验。**

### 9.6 环检测（§7.3）

- **能红的对照**：★ **构造一个 `A → B → A` 的展开链** ⇒ 报错必须**指出那个环**，而不是「深度超限」。
