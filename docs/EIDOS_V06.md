## 1. 归档设计的下落

### 1.1 已经裁定过、而归档文档不知道的

**【已裁】Eidos 变成「内糖」—— 编译器认识它，VM 不需要。**

用人类本人的词（`U195`）：**内糖 = 可直跑；外糖 = 需脱糖**。

- **编译器侧认识 Eidos**：声明、成员、继承、`super`、字段引用由**编译器**解析并**检查** —— 尤其「开放与封闭」（可见性、可继承性、可覆写性）**在编译期判定**。
- **VM 不需要认识它**：编译器把它降到引擎已有的构造（今天的脱糖器做的就是这件事）⇒ **不新增 opcode、不新增运行时类型信息**。
- **被否掉的两条**：① **保持外糖**（「开放与封闭」只能在脱糖期**擦掉**、不能在编译期**守住**）；② **完整内建**（会让 Eidos 成为 VM 的一个新决定点，与去 C 化的方向直接对撞）。

### 1.2 今天的读数

- `src/`、`mods/`、`selfhost/`、`vtest/` **四个目录里 Eidos 零字节**。
- 脱糖器（`tools/eidos_desugar.py`，516 行）的产物**只用了引擎已有的构造**（`func`、字典字面量、闭包、`??`、`record`）。
- 关键字表里有 `record`/`recorded`，**没有 `eidos`/`ed`**。
- **它明确拒绝 Mixin**：脱糖器有一条错误串逐字 `Eidos mixins are not supported by the v0.4 desugar subset`。

★ **解释（不是事实）**：**「零字节不是决定，零字节是零字节」** —— 它同样可以是「停在这儿了」或「还没轮到」，而这三者在今天的树上长得一模一样。**一个形状要被读成裁决，得有人写下它。**

### 1.3 ★ 归档里的 Mixin 与本文的 `@unfold` 是同一件事的两种拼写

归档 §2.5「继承」逐字给出：

```
eidos Dragon: Monster + Flying {   # 多重继承（Mixin）
```

并给出三条规则：**单继承用 `:`，多重继承（Mixin）用 `+`**、**方法查找从左到右，子类优先**、**`super` 调用最近的父类实现**。

★★ **这与人类新提的 `@unfold eidos extend animal, pet` 是同一件事的两种拼写** ⇒ **【待裁】必须裁掉一个**，否则将来两份文档会互相矛盾。

★★★ **而更要紧的是那第三条规则**：**「`super` 调用最近的父类实现」就是位置式 `super`** —— 正是本文 §4 建议要改掉的那一条。**归档在这一点上与新提案直接冲突，而这不是笔误，是一个设计选择。**

### 1.4 归档里今天仍然成立、且是本文前提的部分

| 节 | 内容 | 为什么它仍然成立 |
|---|---|---|
| §2.1 | Eidos 定义 | 与脱糖器一致 |
| §2.3 | 实例化 | 与脱糖器一致 |
| §2.5 | 继承（含 `super`） | 与脱糖器一致（单继承部分） |
| §4.1 | 可见性：公有 `name` / 私有 `_name` | **今天只是「约定私有 + 运行时警告」**，而裁定要求**编译期判定** ⇒ 这一条要改档 |
| §4.2 | `final die` / `final eidos Boss: Monster` | **归档里没有任何实现**；裁定之后它属于**编译期**可判定的一类 |

### 1.5 ★ `invariant` 是唯一一条与「VM 不需要认识它」有张力的

归档 §4.5 逐字：**「每次属性修改后自动检查不变量，违反时触发 `on_violation`。」**

- 另外四条封闭手段（可见性、`final`、`sealed`、`frozen`）**都在编译期判定** ⇒ 与裁定严丝合缝。
- **`invariant` 不是**：它要求**每一次属性写入之后**执行一段用户代码。★ 这有两条实现路：
  - **(a) 编译器把它降到已有的构造**（在每次赋值后插入一次调用 + 一个失败分支）⇒ **VM 仍然不需要认识 Eidos** ✓ 与裁定一致。
  - **(b) VM 认识 `invariant`** ⇒ 与裁定冲突。

⇒ **【提案】走 (a)。** 而它有一个必须写下来的代价：★ **它把「每次属性写入」变成一个语义上非平凡的位置** —— 编译器必须在**所有**写入点（含容器元素、含 `frozen` 之外的路径）插入检查，**漏一个就是一个静默失效的不变量**。★ **这条的验收见 §9.5。**

## 2. 两个标记的形状

**【提案】** 人类给出的形状：

```
@template eidos animal {
    bark {}
}
@template eidos pet {
    bark {}
    play {}
}
@unfold eidos extend animal, pet {
    play { super }
}
```

展开为：

```
eidos cat {
    bark {}
    play {}
}
```

### 2.1 `@template`

**声明一个模板类：不能创建实际对象。**

★ **它必须能非零地回答两个问题，而这两个问题今天的提案里没有写**：

1. **模板能出现在类型位置上吗？** `f(x: animal)` —— 而 `animal` 不是任何对象的类型。
2. **模板能被别的模板 `extend` 吗？** `@template eidos c extend a, b` —— ★ 若能，则 `@template` 与 `@unfold` 的组合有无限多种，**环检测（§7.3）就是必需的而不是可选的**。

### 2.2 `@unfold`

**标记一个类或宏，在编译前展开（如同外糖）。**

★ **「如同外糖」这句话与 §1.1 的裁定有张力**，而它需要被说清：★ **外糖的意思是「展开发生在编译器之前」，而裁定的意思是「编译器认识它」。** 两者可以同时成立，**但只在一种写法下**：

> **编译器做展开，而不是外部工具做展开。** 展开的**语义**由编译器负责（所以它认识 Eidos 的封闭规则）；展开的**结果**是一份编译器内部的东西（所以它不需要 VM 认识）。

⇒ **【提案】`@unfold` 由编译器执行，不是 `tools/` 里的一个脚本。** ★ 否则封闭规则（`final`/`sealed`/`frozen`）永远只能在展开期**擦掉**，而这正是被否掉的那条路。

## 3. 合并规则

**这是整个设计的重心。** 三条规则里，第一条需要重写，第二条需要一句现在还没有的话，第三条需要一个现在还没做的选择。

### 3.1 ★★★ 第一条：同名且相同 ⇒ 只保留一份

**人类给的规则**：「如果两个同名方法相同（如这里的 `bark{}`），只保留一份」。

★★★ **问题：「相同」把「两个函数体的相等」变成了一个语义原语，而文本相同不是语义相同。** 真正的后果是：

> 今天 `animal.bark` 与 `pet.bark` 文本一样 ⇒ 合并成一份。
> 明天有人改了 `animal.bark` 的一个字 ⇒ **`cat` 变了，而没有人编辑过 `cat`。**

★ **这比通常的「脆基类问题」更坏一层**：正常继承里，改基类影响子类是**预期内**的；而这里，**同一次编辑可能改变 `cat`、也可能不改变 `cat`**，判据是**一个从来没有人写下来的性质**。

★★★ **这种耦合没有任何读数能看见它** —— 它不是「一个数没印出来」，是**「这条边存不存在」本身没印出来**。

**三条可选路：**

- **(a) 纯静默合并**（今天提案写的）—— 简单，但上面那个洞永远在。
- **(b) 相同也必须显式**：写 `bark from animal`，文本一样也不自动合。
- ★ **(c)【提案】静默合并，但【必须报出来】，且这个报告本身可被钉住。**

**(c) 的形状**：编译器输出一行 `merged: animal.bark == pet.bark (identical bodies)`，**并允许把这一行钉成一条断言** ⇒ **哪天它们不再相同，那条钉会红，而红的地方正是当初做合并决定的地方。**

★ **理由（与本仓库已有的家法一致）**：**值 + 守卫 = 安全；值 + 无守卫 = 病。** 合并是一个值，而它在今天这个提案里**没有守卫**。

### 3.2 ★★ 第二条：同名而不同 ⇒ 必须覆写

**规则本身对。** 但它把**一个歧义**呈现成了**一个命令**。作者看到的会是一句「你必须覆写 `bark`」，然后他写一个 `bark{}` —— ★ **而这一覆写同时丢掉了 `animal.bark` 与 `pet.bark` 两份实现，且没有任何东西告诉他丢的是哪两份。**

**【提案】诊断必须点名来源，并给出「只取一份」的写法：**

```
error: `bark` comes from `animal` and `pet` with different bodies
  → override it here (discards both), or
    keep one:  bark from animal
```

★ 理由：**「另一条路是什么」必须写出来，否则读者以为只有一条路。**

### 3.3 ★★★ 第三条：参数不同不算同名 —— 而「保证不存在重叠」有两个相反的答案

**人类给的规则**：「名称相同但参数不同的不视为同名方法（`run a:float` / `run a:int` / `run{}` 三个不同），但编译器必须通过集合关系保证不存在参数重叠」。

★ **「保证不存在重叠」是【不相交】方案。而人类举的例子里那个 `run{}` 恰好是它排除掉的东西** —— 零参签名是**兜底**，而兜底与特化**必然重叠**。

| | **不相交**（今天提案写的） | **最特化优先**【提案】 |
|---|---|---|
| 规则 | 任意两个签名不得相交 | 允许相交，**更特化的赢**；只有**互不更特化**才算歧义 |
| `run a:int` + `run a:Z` | **非法** | 合法，传 `int` 走 `int` 那支 |
| `run{}` 兜底 | **与所有签名冲突 ⇒ 写不出来** | 合法，兜底最不特化 |
| 要证的义务 | **所有两两配对都不相交** | **只有实际相交的那几对要能分出胜负** |
| 判据的难度 | 集合表达式的一般相交判定（算子一多就很难，甚至不可判定） | 只比较两个签名，**可判定** |

**【提案】取「最特化优先」**，三条独立的理由：

1. **人类自己举的 `run{}` 只有在最特化优先下才有意义。**
2. **证明义务要尽量小**：不相交是对**所有配对**的证明；最特化只对**真正重叠的配对**证明。★ 而这是一个**集合式类型系统** —— 集合表达式上的相交判定会随算子增长而变贵。
3. **不相交会把「我想给 `int` 一个特例、其余走通用」这条最常见的需求变成写不出来。**

★★ **还有第三条路，而它最像这个仓库的脾气**：**编译器不判「有没有重叠」，它报出【重叠的那块类型】** —— 「`run a:int` 与 `run a:Z` 在 `int` 上重叠」。★ **是报，不是拒。** 这与本仓库反复出现的形状一致（**记录 vs 指针**、**一个零要能被归因**）。

### 3.4 ★ 字段的合并规则与方法不同，而今天没有写

方法「相同就合、不同就覆写」。★ **字段「同名不同默认值」不是覆写，是一个没有自然解的冲突** —— 取哪个默认值？

**【提案】单列一条规则，且报错时把两个默认值都印出来：**

```
error: field `hp` has different defaults: `animal.hp = 10`, `pet.hp = 20`
  → restate it here with one value
```

## 4. ★ `super` 必须限定

**人类给的例子里 `play { super }` 里的 `super` 指向谁？** ★ 这个例子里 `play` 只在 `pet` 里，所以无歧义；**但规则必须现在写**，因为一旦两个父都有 `play`，位置式 `super` 就是多重继承里最难推理的那一部分。

★ **而归档 §2.5 已经把位置式写成了规范**：「`super` 调用最近的父类实现」。

**【提案】`super` 必须带名字** —— `super pet.play`（或 `super(pet)`）。

★ 理由：**这个语言的全部卖点是「编译期可判定」，而位置式 `super` 把这个卖点直接交出去** —— 它让「这段代码调用的是哪个实现」取决于**父列表的顺序**，而那个顺序在展开之后**看不见了**（§5）。

---

## 5. ★★ 展开必须带出处

**人类给的规则**：`@unfold` **在编译前展开，如同外糖**。★ 那么**编译器看到的是展开后的东西** —— **于是「`cat` 的第 3 行」这类报错会指向生成物。**

★★ **这是宏系统最经典的问题，而它有一个便宜的解法**：**展开产物必须带源位置映射**（哪个成员来自哪个模板的哪一行）。

★ **顺带它也解决了 `reflect`** —— 人类之前要过 `reflect` 标签，而「这个方法来自 `pet`」正是它该报的东西。

★★★ **一条原则**：**展开是【指针】（这个类今天长什么样），出处是【记录】（它从哪来）。两个都要，而且它们不是同一个东西。**

- **只留展开结果** = 丢掉了记录 ⇒ 报错指不到源，`reflect` 说不出出处，合并决定不可审计。
- **只留出处** = 每次都要重算 ⇒ 而这正是「编译期展平」要避免的。

## 6. 命名

### 6.1 `@template` 这个名字会被读错

在几乎所有语言里 `template` 意思是**泛型**（C++ templates、Java generics）。★ 而这里它意思是**抽象 mixin**。

**【提案】改用 `@mixin` / `@trait` / `@abstract`。** ★ 理由：**将来真的想要泛型时，`@template` 已经被占了。**

### 6.2 与归档的拼写冲突

见 §1.3：**`@unfold eidos extend A, B` 与 `eidos C: A + B` 是同一件事的两种拼写** ⇒ **【待裁】必须裁掉一个。**

## 7. 尚未写的三件（一旦落地就会被问到）

### 7.1 字段怎么合 —— 见 §3.4

### 7.2 `@unfold` 可传递吗？

**`@unfold` 的结果是模板还是类？** ★ **能再展开就定义链，不能就定义深度 1。**

### 7.3 循环展开检测

`A` 展开需要 `B`，`B` 需要 `A`。★ **必须有环检测，且报出那个环**（不是「深度超限」）。

★ 理由：**「深度超限」是一个关于实现的读数，「这是一个环」是一个关于设计的读数** —— 前者让作者去调一个上限，后者让他去改结构。

## 8. 与其他语言的关系（缺的那一半）

## 9. 每条规则的验收

★ **每一条规则配一个最小例子 + 一条能红的对照。** 这是本文与归档文档最大的形式差别：**归档全是陈述句，而陈述句不能红。**

### 9.1 合并（§3.1）

- **例子**：§2 那两个模板 + `@unfold`。
- **能红的对照**：★ **改 `animal.bark` 的一个字** ⇒ 若走 (c)，**那条「merged」的钉必须红**；若走 (a)，**什么都不会红** —— 这正是 (a) 与 (c) 的可区分之处。

### 9.2 歧义诊断（§3.2）

- **能红的对照**：★ **删掉诊断里那句 `keep one: bark from animal`** ⇒ 必须有一条断言红（★ **否则「诊断会点名来源」这句话没有守卫**）。

### 9.3 参数重叠（§3.3）

- **例子**：`run{}` / `run a:int` / `run a:Z` 三者并存。
- **能红的对照**：★ **传一个 `int` 实参** ⇒ 若走「最特化优先」，必须走 `run a:int`；★ **若走「不相交」，这个程序必须编译不过** —— **两种方案在这个例子上给出相反的可编译性，所以它是可判别的。**

### 9.4 `super` 限定（§4）

- **能红的对照**：★ **交换 `extend` 里两个父的顺序** ⇒ 若走位置式，**行为必须变**；若走限定式，**行为必须不变**。★ **「顺序无关」这条性质本身，就是这个方案要买的东西。**

### 9.5 `invariant` 的写入点覆盖（§1.5）

- **能红的对照**：★ **构造一个能绕过检查的写入路径**（容器元素、嵌套字段、`frozen` 之外的第二条路）⇒ 若它**能**绕过，说明写入点的枚举不全。
- ★ **这一条必须现在做**，因为它是 §1.5 那条「编译器把它降到已有构造」的**唯一验收**：★ **「每次属性修改后自动检查」里的「每次」是一个全称量词，而全称量词只能靠枚举来验。**

### 9.6 环检测（§7.3）

- **能红的对照**：★ **构造一个 `A → B → A` 的展开链** ⇒ 报错必须**指出那个环**，而不是「深度超限」。
