> **这份文件是什么**：v0.6 的**工作计划** —— 范围、顺序、三条主线各自的现状与交付项、验收判据、以及**未定与冲突**。

| **C. 本会话的实测** | 引擎源码、`ctest`、门禁各阶段 | 给命令与读数，不给「概述」 |

**三条纪律（本文自己服从）：**

1. **一个量要么带它的观测点，要么不许写成现值。** 「今天有 N 个」这种句子旁边没有 ref 的话，下一笔提交就会让它变假，而**变假时没有人会说话**。
2. **三分清单：已实现 / 部分 / 未实现** —— 而「已实现」的定义就是第 3 条（必须能指出盯着它的那条测试）。**另有一层与它正交、不许与它混用：只是设计 / 只是计划**（有没有代码，与有没有测试盯着，是两个问题；本文件第一版把两层写成了一套名字下的两个三分的，见 §7 收录判据那段）。仓库自己判过「设计未实现」的（如 Inim OS），本文照抄。
3. **凡说「已实现」，必须能指出盯着它的那条测试。** 没有测试盯着的「已实现」是叙述，不是状态。
4. ★ **引文也带观测点 —— 与第 1 条并列，不是并进它。** 上一轮读过的原文，这一轮要么**重取**，要么给它标上「**读于 `<sha>`**」。理由不是洁癖，是一条实测出来的机制：
   - 行号那件事早就立过规矩（位置形式的引用必须能回到产生它的那棵树），**而引文一直不在那条规矩的射程里** —— 那条只管「文件名:数字」。
   - **一条引文也是一条读数，而它需要自己的观测点。带着走的引文没有观测点，所以它过期时没有任何东西会红。**
   - 它发生的条件比「两棵树不同」宽得多：**只要「上一轮读过、这一轮接着用」就会发生，而它恰好是写报告时最自然的动作。** 同一份报告里，**数据是重取的、引文是带过来的** —— 这个不对称本身就是病征。
   - 实测实例（本文件自己）：一份独立复核引用了第 2 条的原文，**引用时逐字正确**；而**把它变旧的那一笔，正是把那次复核的结论落进本文件的那一笔**。它不是读了一棵旧树 —— **作废通知是随更正一起到的：在读数被取走的那一刻，树上没有任何东西标记它是即将作废的。**（第 2 条那句「本文件第一版把两层写成了一套名字下的两个三分的」，是更正那一笔**同时**补上去的。）
   - ★ **所以「带着走的引文」不是一种疏忽，是一种没有对照物的状态：它只能在事后被发现。** 这一句决定第 4 条是**可执行的规矩**还是**道德劝告**：如果读者本可以看见通知而没看，结论只能是「下次仔细点」；如果读者不可能看见，结论只能是机制 —— **要么重取，要么给它盖上「读于 `<sha>`」。只有后者能防下一次。**
   - ★ **它的复发间隔可以短到一条消息**：提出第 4 条的那个人，在**更正一条引文错**的同一条消息里，**又写下了一句时态错的引文**（把「作废通知随更正一起到」写成了「它自己已经宣布作废」）。⇒ 这条纪律不是洁癖：**一个已经警觉的人，在刚刚立下它之后一条消息，就又犯了一次。**

## 3. 三条主线

### 3.1 进一步去 C 化

**权威**：[`docs/DECFY_DESIGN.md`](DECFY_DESIGN.md)（工作订单 `task-16`）。它的状态行自己写着「设计（未实现的部分仍未实现）」。

**它的核心论点（逐字）：**

> **「用 `.im` 重写」不是修法。** 本题的难点不是「哪个文件是 C」，而是同一条语言语义在仓库里有多个独立决定点，且这个分裂横切实现语言。

**最硬的证据**：`selfhost/compiler.im` 与 `selfhost/eval.im` **都是 `.im` 写的**，却对 `and`/`or` 给出相反答案（前者值语义、后者布尔）。⇒ **换成 `.im` 本身不消除分歧，只是改变分歧发生在哪两个文件之间。**

**已落地（`docs/DECFY_DESIGN.md` §0.5 落地现状表，逐条锚定 commit）：**

| 原论断 | 现状 |
| --- | --- |
| `and`/`or` 六个决定点 | **已修**：统一为布尔语义、短路保留；判据换成**三后端逐格比对** |
| `%` 三决定点、32 位截断 | **已修**：16/16 三后端一致 |
| 宽度契约分裂（`Value` 32 位 vs AOT `NV` 64 位） | **已修**：匿名 union 把 `ival` 改 `long long`，`sizeof(Value)` 仍 32，AOT 的 `NV` 未动 |
| `OP_AND`/`OP_OR` 是死指令 | **已过期**：两者今天都是活的 |
| 「真值产生点唯一」 | **已实现**：`vm_truthy()` 单入口 |

**未做的那一件，也是本题的核心：**

> §3「IR 收敛」（后端改吃字节码）—— **未做，是「未做的下一步」，不是「已被取代」**。

**实测把这件事量化了**（观测点：`main @ f6e22f5` 的 `src/` 全树；**命令与读数一起给**）：

- `grep -rn 'emit_from_bytecode' src/` → rc=1、**零命中** ⇒ 后端今天仍**各自遍历 AST**，结构成因一点没动。
- `grep -c 'OP_' src/compilation/aot_native.c` = **0**；`grep -oE 'case OP_[A-Z0-9_]+' src/compilation/aot_native.c | sort -u | wc -l` = **0**。
- `grep -c 'OP_' src/compilation/wasm_backend.c` = **1**，而它唯一的命中是一句注释（`OP_LT double compare`）⇒ **两个后端里没有一个活的 opcode 消费者**。
- **VM 69/69** ⇒ **今天只有 VM 认识字节码**。
- 这四条由独立复核者逐条重跑确认（4/4 成立，一条都没被推翻）。

**交付项：**

1. **决定点清单（必须先做）。** 这是本件的**第一个交付物，也是最小的一件**：把「同一条语言语义在仓库里有几个独立决定点」逐条列出来（`and`/`or`、`%`、真值、`in`/子集/`be`、……），每条给出**它今天有几个决定点、分别在哪个文件、各自被谁消费**。**没有这份清单，后面每一件修的都是碰到的第一个。**
2. **IR 收敛**：让所有后端消费同一个 IR（字节码），把语义从「每个消费者各自重判一次」收敛成**一张表**，使分歧在结构上不可表达。
3. **迁移与诊断**：收敛过程中每条语义的迁移路径，以及分歧出现时的可定位诊断。

**诚实边界（必须写在任何对外陈述里）：**

- 用户本人在语料里说过（`U072`/`U076` 逐字）：「目前核心和所有模组均已去C化」。**这句话与仓库冲突** —— 按 §3 的判据，核心的去 C 化**没有完成**。这条冲突**不许在计划书里被抹平**（见 §7）。
- 「设计已交付」不等于「实现已完成」。`docs/DECFY_DESIGN.md` 的多节被实现方**当规格引用**（这本身是好事），但那说明的是**设计可执行**，不是**题目已解**。

### 3.2 集合化类型系统

**权威**：[`docs/TYPESET_V06.md`](TYPESET_V06.md)。**现行 v0.6 目标**（`docs/STATUS.md`）。

**已有雏形（有 CTest 覆盖）—— 但「已实现」的那一条必须按今天的语法读：**

- 内置集合、集合字面量、区间、推导式 —— 解析器侧已实现。
- **约束绑定：解析器 → 编译器 → VM 三段已通 —— 而它的拼写已经换了。** `be` 于 `c89e077`（2026-10-05）被**移除**：`docs/SYNTAX.md` §6.3 逐字 `name: <集合或表达式> [= 初值]  // 现行唯一形式`、`name be <集合或表达式> [: init]  // 已移除：报错，不静默`。实测 `x be 1,2,"男",false` → `Error at line 1: 'be' declarations were removed (docs/SYNTAX.md 6.3); write 'name: set [= init]' in place of 'name be set [: init]'`。**而机制是活的**：`x: 0,1,2,3 = 2` → `say x` = `2`；`x = 9` → `[exception] uncaught: type_mismatch`（RC=1）⇒ **`be` 的拼写被移除，`be` 的语义没有。**
- 集合运算（`+` / `*` / `-` / `in`）已实现；**而 `set(arr)` 今天不存在**：`say set([1,1,2])` → `unknown builtin function 'set'`；`s: set = [1,1,2]` → `say s` = `[1, 1, 2]`、`say len(s)` = **3**（**不去重**）；`s + t` → `Error: '+' is not defined for arrays/dicts` ⇒ **「从数组生成集合」今天没有对应构造**（`U214` 因此是**未实现**，见 §5.2）。
- 另：`1..3` 在**表达式位**是解析错误（`expected 'expression', but got '..'`）⇒ 区间只在集合语境里成立。
- ⚠ **★ 三种拼写三种东西，而文档 §6.3 给的例子是最不生效的那一种。** 独立复核（`noble-zephyr`）实测：
  - `age: [0, 120] = 18` ⇒ **`[0, 120]` 是一个数组（`EXPR_LIST`），不是集合** ⇒ **不产生约束**（`age = 200` 被接受、RC=0）。
  - `age: [0~120] = 18` ⇒ `~` 是区间 ⇒ **有约束**（`age = 200` → `type_mismatch`，rc=1）。
  - `age: 0, 120 = 18` ⇒ **`0, 120` 是集合 {0, 120}，不是区间 0..120** ⇒ 18 ∉ {0,120} ⇒ `[exception] uncaught: initial value out of range`（rc=1）。
  - ⇒ **`~` 是区间、`,` 是枚举、`[...]` 是数组** —— 三种拼写三种含义，**而文档用的那个恰好是最不生效的**。

- ⚠ **★ 而它的定性要分两层，只写一层会把一个缺陷写成一次笔误：**
  - **语法层 = 未收敛，不是缺陷。** `looks_like_set_start`（`src/parser/parser.c`）是一个**启发式**，只认三种开头（数字/字符串 + `,`、标识符 + `,`、标识符 + `[`/`(` 且像区间），**从不认开头的 `[`** ⇒ `[0, 120]` 必走 `parse_expr` 得到 `EXPR_LIST`（数组），而 `0,1,2,3` 走 `parse_set_literal` 得到 `EXPR_SETLIT` → 发 `OP_NEW_SET`。**两种写法落成两个不同的表达式节点** ⇒ 按 §3.1 的判据，**这是未收敛，该进决定点清单**。
  - **VM 层 = 缺陷。** `L_BIND` 里逐字 `int sidx = (R[setReg].type == VAL_SET) ? R[setReg].ival : -1;` 与 `vm->global_bound[g] = sidx >= 0 ? sidx + 1 : 0;` ⇒ **绑定表达式求值结果不是集合时，静默退化成「无约束」，一个字不报**，初值检查也被 `sidx >= 0` 短路。**而同一份引擎在同类地方是拒绝的**（`be` 的移除逐字「报错，不静默」；重复内建逐字「Refuse the duplicate and name it, instead of losing it silently」）⇒ **这里缺的正是同一条纪律。**
  - **★ 同一条静默路径有第二个入口，第一轮两个复核者都没量到**：`x: NoSuchSet = 5` 之后 `x = 999` → **rc=0、照常执行** ⇒ **未定义标识符当约束，同样静默无约束**。⇒ **不是只有括号形式会掉进去，任何求值结果不是集合的绑定表达式都会。**
  - **正面控制（机制本身是好的）**：`x: 0,1,2,3 = 2` → `x = 9` → `type_mismatch`（rc=1）；`x: N = 5` → `x = -1` → `type_mismatch`（rc=1）。
  - ★ **机制是统一的，不是「某种写法碰巧对」。** 四臂对照（`noble-zephyr`，同一台 `build/inimerse`）：
    - `type Byte = [0~255]` + `x: Byte = 42` + `x = 999` ⇒ 打 `A decl Byte = set(R interval)`，然后 `[exception] uncaught: type_mismatch`（rc=1）⇒ **生效**。
    - 同一段**去掉那句声明** ⇒ 打 `undecl Byte = nil`，然后 `reached`（rc=0）⇒ **静默无约束**。
    - `x: N = 5` + `x = -1` ⇒ `type_mismatch`（rc=1）⇒ **生效**（`N` 求值为 `set(N)`，是内建预设）。
    - `x: NoSuchSet = 5` + `x = 999` ⇒ `reached`（rc=0）⇒ **静默无约束**。
    ⇒ **四种写法走的是同一条机制**：约束那一格是一个**运行期求值的表达式**，只有求值结果是集合才登记 `global_bound[]`。**⇒ 缺陷的形状是「非集合的求值结果被静默接受」，不是「某种写法碰巧对」。** 这一句对 §3.1 的决定点清单直接有用：**约束的登记点是运行期的一个类型判断，而不是一个语法位置。**
  - ⚠ **一处必须写清的更正**：上一版把 `x: Byte = 42` 当作「第二个入口」的实例 —— **撤回**。`Byte` 是文档里**正确**的那个例子（`docs/SYNTAX.md` §6.3 的旧读数 `Byte=set(R interval)` 今天**逐字可复现**，不是过期），它只在**没被声明**时才退化成 `nil`。**第二个入口的正确实例是未定义的标识符**（`x: NoSuchSet = 5`）。
  - **两条今天会失败的判据**（红对照）：① `age: [0, 120] = 999` → 今天 `say age` = `999`、rc=0，**应被拒**（求值结果是数组）；② `x: NoSuchSet = 5` 后 `x = 999` → 今天 rc=0，**应被拒**（求值结果是 `nil`）。**第三条（`age: [0, 120]` 无初值）降级为佐证**，不构成独立对照 —— 它证明的是同一条机制（无初值时绑定不产生约束）。
  - **处置**：**登记，不现在修**（§8 第 7 条：不改任何引擎源码之前先有决定点清单）。它同时是 §3.1 决定点清单的一条与 §3.2 的一条 —— **这正是两条主线的接缝。**

**★ 「已进 CTest」这句话的强度上限（本文件第一版没说）：** 三个计数 —— 模语义 **16**、逻辑语义 **64**、AOT **104** —— **都没有门禁盯着**。`CMakeLists.txt` 里对应的三条 `add_test` 都**没有** `PASS_REGULAR_EXPRESSION`，`tools/gate.sh` 只钉 fuzz 的三个 `EXP_FUZZ_*` ⇒ **删掉 30 条 `logic_semantics` 用例，它仍会打 `ok (34 cases…)` 并且门禁全绿**。而且「16」唯一的家是 `tools/mod_semantics.test.py` 的一句注释（该文件只 `print len(TABLE)`，无断言）⇒ 这三个数是**值 + 无守卫**，且被转写了三次。**所以「有 CTest 覆盖」今天的意思是「有人跑过它」，不是「它掉下来会有人知道」。**

**要做（`docs/TYPESET_V06.md` §4 的 R1–R6）：**

## 4. 依赖：为什么是这个顺序

**这个顺序不是偏好，是一条已经写在别处的依赖。**

1. **Eidos 变成内糖 ⇒ 依赖去 C 化。** 按 §3.3 的裁定，Eidos 要成为**编译器认识的语义**，它就**必然**是编译器侧的一个新的决定点；而「多个决定点」正是 §3.1 要消掉的东西。**先收敛再进新语义**，否则新语义会变成第七个决定点。

## 9. 验收：怎么算做完了

**四条，缺一条就不算：**

1. **每个交付项要有一条能在 `main` 上失败的进树回归**，并且**断言输出的值，不是退出码**（逐字依据见 §3.2）。
2. **每个读数带观测点**：数字旁边要么有 ref，要么它只是一个 delta。**绝对现值永远非法**（写这句话会不会改变它量的那个数 —— 会，就不能写成现值）。
3. **三分清单**（与 §1 纪律 2 同一套，不是另一套）：任何「已完成」的说法必须能指出盯着它的那条测试；没有测试盯着的，写「部分」或「未实现」。**另有一层与它正交：只是设计 / 只是计划。**
   - ★ **「部分」必须写出缺的是哪一半。** 这个词今天在本文件里承担了两件不同的事：**「有实现、有守卫、但不全」**（§5 的 `U130`/`U161`/`U164` 是这类）与**「只是一个意向，没有实现也没有守卫」**（`U035`/`U070`/`U098` 是这类）。**同一格字面无法区分这两种情况，而它们下一步该做的事完全不同**（前者是补实现，后者是先变成一条可实现的要求）。⇒ **凡写「部分」，同格必须点名：守着它的是哪条测试（或写「没有」），以及缺的是哪一半。** 这条纪律是被量出来的：§5 的「部分」格共 **15 格**，其中 **9 格当时没有任何测试盯着**。
4. **冲突不抹平**：§7 表里每一条，在它被裁定之前，**以「未定」出现在所有对外陈述里**。

**第一个里程碑（最小、且必须先做）：**

> **决定点清单。** 逐条列出「同一条语言语义在仓库里有几个独立决定点、分别在哪个文件、各自被谁消费」，覆盖 §3.1 与 §3.2 两处。**它是后面每一件的前提，也是唯一一件可以只靠读码完成的。**
