# Inimerse v0.6 计划书

> **这份文件是什么**：v0.6 的**工作计划** —— 范围、顺序、三条主线各自的现状与交付项、验收判据、以及**未定与冲突**。
> **不是什么**：不是规范。规范是 [`docs/TYPESET_V06.md`](TYPESET_V06.md)（集合化类型系统）与 [`docs/DECFY_DESIGN.md`](DECFY_DESIGN.md)（底层去 C 化设计）；本文只做「按什么顺序、先做哪一件、做到什么算做完」。
> **也不是承诺**：本文标「未实现」的，就是**没有开始**。凡仓库自己判过「设计未实现」的，本文照抄，不美化。

## 0. 一句话

**v0.6 = 进一步去 C 化 + 集合化类型系统 + Eidos，按「去 C 化 → Eidos 进引擎 → Inim OS」推进；Inim OS 不在 v0.6 内。**

这三件不是三条腿，是**一条依赖链**（§4）。

## 3. 三条主线

### 3.1 进一步去 C 化

**权威**：[`docs/DECFY_DESIGN.md`](DECFY_DESIGN.md)（工作订单 `task-16`）。它的状态行自己写着「设计（未实现的部分仍未实现）」。

**它的核心论点（逐字）：**

> **「用 `.im` 重写」不是修法。** 本题的难点不是「哪个文件是 C」，而是同一条语言语义在仓库里有多个独立决定点，且这个分裂横切实现语言。

**最硬的证据**：`selfhost/compiler.im` 与 `selfhost/eval.im` **都是 `.im` 写的**，却对 `and`/`or` 给出相反答案（前者值语义、后者布尔）。⇒ **换成 `.im` 本身不消除分歧，只是改变分歧发生在哪两个文件之间。**

**已落地（`docs/DECFY_DESIGN.md` §0.5 落地现状表，逐条锚定 commit）：**

| 原论断 | 现状 |
| --- | --- |
| `and`/`or` 六个决定点 | **已修**：统一为布尔语义、短路保留；判据换成**三后端逐格比对** |
| `%` 三决定点、32 位截断 | **已修**：16/16 三后端一致 |
| 宽度契约分裂（`Value` 32 位 vs AOT `NV` 64 位） | **已修**：匿名 union 把 `ival` 改 `long long`，`sizeof(Value)` 仍 32，AOT 的 `NV` 未动 |
| `OP_AND`/`OP_OR` 是死指令 | **已过期**：两者今天都是活的 |
| 「真值产生点唯一」 | **已实现**：`vm_truthy()` 单入口 |

**未做的那一件，也是本题的核心：**

> §3「IR 收敛」（后端改吃字节码）—— **未做，是「未做的下一步」，不是「已被取代」**。

**实测把这件事量化了**（本会话，`src/` 全树）：

- `emit_from_bytecode` 在 `src/` **零命中** ⇒ 后端今天仍**各自遍历 AST**，结构成因一点没动。
- 引用 opcode 的个数：`src/compilation/aot_native.c` **0**、`src/compilation/wasm_backend.c` **1**（而那唯一一个还在注释里）、**VM 69/69**。

**交付项：**

1. **决定点清单（必须先做）。** 这是本件的**第一个交付物，也是最小的一件**：把「同一条语言语义在仓库里有几个独立决定点」逐条列出来（`and`/`or`、`%`、真值、`in`/子集/`be`、……），每条给出**它今天有几个决定点、分别在哪个文件、各自被谁消费**。**没有这份清单，后面每一件修的都是碰到的第一个。**
2. **IR 收敛**：让所有后端消费同一个 IR（字节码），把语义从「每个消费者各自重判一次」收敛成**一张表**，使分歧在结构上不可表达。
3. **迁移与诊断**：收敛过程中每条语义的迁移路径，以及分歧出现时的可定位诊断。

**诚实边界（必须写在任何对外陈述里）：**

- 用户本人在语料里说过（`U072`/`U076` 逐字）：「目前核心和所有模组均已去C化」。**这句话与仓库冲突** —— 按 §3 的判据，核心的去 C 化**没有完成**。这条冲突**不许在计划书里被抹平**（见 §7）。
- 「设计已交付」不等于「实现已完成」。`docs/DECFY_DESIGN.md` 的多节被实现方**当规格引用**（这本身是好事），但那说明的是**设计可执行**，不是**题目已解**。

### 3.2 集合化类型系统

**权威**：[`docs/TYPESET_V06.md`](TYPESET_V06.md)。**现行 v0.6 目标**（`docs/STATUS.md`）。

**已有雏形（有 CTest 覆盖）：**

- 内置集合、集合字面量、区间、推导式 —— 解析器侧已实现。
- `be` 约束绑定：解析器 → 编译器 → VM 三段已通。
- 集合运算（`+` / `*` / `-` / `in`）与 `set(arr)` 已实现。

**要做（`docs/TYPESET_V06.md` §4 的 R1–R6）：**

| | 交付项 |
| --- | --- |
| **R1** | `type` 成为**唯一**的定义形式，且**至少被编译期消费一次** |
| **R2** | `Z` 任意精度；`int`/`int32`/`int64` 降为子集别名 |
| **R3** | 位宽由基数派生 + `@bits(n)`/`@bytes(n)` 编译期校验 |
| **R4** | 无法证明范围时**保留符号表示** + 可定位的运行时检查 |
| **R5** | ABI / 序列化边界宽度必须由一条 `type` 给出 |
| **R6** | 溢出语义与集合一致 |

**另加一件，与 3.1 是同一个问题：**

> **消去「同一语义多决定点」** —— `in` / 子集 / `be` 各收敛为**唯一决定点**。

**这一句是两条主线的接缝**：3.1 说的是「后端各自遍历 AST 导致语义分歧」，3.2 说的是「`in`/子集/`be` 各自重判导致语义分歧」——**它们是同一个病在两个层次上的两次发作**。所以 §3.1 的**决定点清单**必须同时覆盖这两处。

**验收（本件最硬的一条，逐字引自 `docs/SYNTAX.md`）：**

> 退出码与「跑得动」都完全掩盖它……**任何回归必须断言数值。**

⇒ **每一个交付项都要有一条能在 `main` 上失败的进树回归，且必须断言输出的值，不能只断言退出码。**

**非目标（已裁定）：** `FloatN` 已移出核心；不把不可判定谓词伪装成编译期证明；未出规范前不改 `in` 语义；不承诺 BigInt 性能。

**这一件是三件里唯一连设计文档都没有的。**

**现状（仓库自己的判词）：**

- `docs/API.md` 逐字：**「已实现（仅经外部工具）/ 核心前端零实现」**，以及**「引擎本身不认识 Eidos」**。

- 有两条 CTest 盯着它：`eidos_desugar_runtime`、`eidos_runtime`。
- `grep -rn eidos src/` **零命中**。

**用户问过、而至今没有答案的那个问题**（`U111`/`U112` 逐字）：

> 「将sprite进行面对对象化重构；**如何进行 eidos 的开放和封闭**」

⇒ **「开放和封闭」这件事，连一份设计文档都不存在。**

**交付项（顺序上分两步，第一步必须先做）：**

1. **设计文档**：Eidos 的**开放与封闭**是什么、边界在哪、与集合化类型系统怎么结合（用户 `U190` 逐字要的是「通过更好的集合语言定义类型、对象和函数」，`U191` 要「更先进的解法」）。**这一步的产物是一份设计，不是代码。**
2. **进引擎**：让引擎前端**认识** Eidos —— 或者，明确裁定「Eidos 永远是外部脱糖工具」。

**★ 今天的读数（普查：[`docs/streams/eidos-state.md`](streams/eidos-state.md)）**

- **读数（是事实）**：`src/`、`mods/`、`selfhost/`、`vtest/` **四个目录里 Eidos 零字节**；脱糖器的产物**只用了引擎已有的构造**（`func`、字典字面量、闭包、`??`、`record`）；`src/lexer/lexer.c` 的关键字表里有 `record`/`recorded`，**没有 `eidos`/`ed`**。⇒ **引擎今天不认识 Eidos，而工具链的产物不需要它认识。**
- **解释（不是事实，是判断）**：上面这个形状**不等于**「有人选过『永远外部』」。**零字节不是决定，零字节是零字节** —— 它同样可以是「停在这儿了」或「还没轮到」，而这三者在今天的树上长得一模一样。**一个形状要被读成裁决，得有人写下它。**
- **另两条读数**：盯着 Eidos 的两条测试里**只有一条断言数值**；而**那一条的比较先做了一次白名单过滤**（只保留属于 `{'3','4','7','9'}` 的行，再比最后六个）⇒ **额外输出不会被发现，值域内的错值也不会被发现**。另有一个 `vtest/` 下的样本文件被允许「没有测试跑它」，**理由是另一条测试断言了这个特性**，而那条测试就是上面这条过滤后的比较。

**★ 第 2 步的两个答案都是合法的，但必须被明确选一个：**

- 选「进引擎」⇒ 它就是一个引擎侧的语义决定点 ⇒ **它必然落进 §3.1 的决定点清单**，并且**依赖 IR 收敛**。
- 选「永远外部」⇒ 那么「Eidos 进引擎」这条依赖链就断了，**Inim OS 的前置也就不成立**（§4），必须回头改 §2 的顺序。

**相关要求（他本人说过的，落在本件范围内的）：** 集合式 OOP、多细胞对象、`reflect` 标签、覆写（子类覆写父类函数 / 子细胞覆写管家基因）、宏与多分派统一、`.java`/`.class` 转写 —— 逐条见 §5.3。

## 4. 依赖：为什么是这个顺序

**这个顺序不是偏好，是一条已经写在别处的依赖。**

1. **Eidos 进引擎 ⇒ 依赖去 C 化。** 若 Eidos 要成为引擎认识的语义，它就**必然**是一个新的决定点；而「多个决定点」正是 §3.1 要消掉的东西。**先收敛再进新语义**，否则新语义会变成第七个决定点。
2. **Inim OS ⇒ 依赖 Eidos。** 依据逐字（`future/archive/Inim OS总纲.md`）：**「以 Eidos 为对象模型」**。
3. **Inim OS 自己的文档说了它要什么**：内核用「编译后」档 ⇒ 它要的是一个**已收敛的编译器**，不是一个还在多决定点状态的编译器。

⇒ **去 C 化 → Eidos 进引擎 → Inim OS**，而 **Inim OS 的每一项前置都落在 v0.6 之外**，这正是它不在 v0.6 内的原因（不是因为不重要，是因为**它前面的两件没做完时它做不动**）。

## 9. 验收：怎么算做完了

**四条，缺一条就不算：**

1. **每个交付项要有一条能在 `main` 上失败的进树回归**，并且**断言输出的值，不是退出码**（逐字依据见 §3.2）。
2. **每个读数带观测点**：数字旁边要么有 ref，要么它只是一个 delta。**绝对现值永远非法**（写这句话会不会改变它量的那个数 —— 会，就不能写成现值）。
3. **三分清单**：任何「已完成」的说法必须能指出盯着它的那条测试；没有测试盯着的，写「部分」或「未实现」。
4. **冲突不抹平**：§7 表里每一条，在它被裁定之前，**以「未定」出现在所有对外陈述里**。

**第一个里程碑（最小、且必须先做）：**

> **决定点清单。** 逐条列出「同一条语言语义在仓库里有几个独立决定点、分别在哪个文件、各自被谁消费」，覆盖 §3.1 与 §3.2 两处。**它是后面每一件的前提，也是唯一一件可以只靠读码完成的。**
