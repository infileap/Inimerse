# 去C化：一页纸的进度读数

**这份文档回答一个问题：这个仓里，去C化（把引擎实现从 C 搬到脚本语言一侧）进行到哪一步了。**

**答案是：测不出来。下面是我怎么得出这句话的，以及什么会让它变。**

（2026-10-25 补记：第三条「可执行的等价判据」已经落地成一件量具，见下文的第四把尺子 —— 它没有把这句话变成「测得出来」，但它把「同名」那一格换成了「C 的调用还在不在路径上」，这一格是可机械判的。）

## 怎么读这份文档

引擎有两套源码：一套是 C，一套是仓里自己的脚本语言（后缀 `.im`）。「去C化」指的是把前者的实现搬到后者。

**我用了四把尺子。它们量的是四件不同的事，所以它们给出的百分比不能相加、也不能平均 —— 四个都印出来。**

- **体量尺子**：C 源与脚本源各占多少。同一件事有三种口径（文件数 / 字节 / 行数），**三种分开印**。
- **能力尺子**：引擎对外提供的每一个能力（一个具名函数），有多少是**只有 C 实现**、脚本一侧没有对应物。
- **调用链尺子**：从脚本一侧的入口出发，被调用到的名字里有多少在脚本一侧有实现。

## 两棵树

- **树 A** = 发布线停住的那一点（版本 v0.5.2 指向的提交）＝ `322c085da2f83b93d22da436ebf322fa5f52b081`。**它是记录，不跟着主干动。**
- **树 B** = 我量的那一刻的主干 ＝ `f49a9a5919a57fff8637ceb3510bbfc8a5b60035`。

**下面每一个数都标出它是在哪棵树上量的。**

|---|---|---|---|
| 文件数：C 占 C＋脚本 的比例 | 31.91% | 31.85% | −0.07 个百分点 |
| 字节：同上 | 91.90% | 91.60% | −0.30 个百分点 |
| 行数：同上 | 83.19% | 83.02% | −0.17 个百分点 |

## 第四把尺子：C 的调用还在不在脚本那一侧的路径上（可执行判据）

前三个尺子都在数**名字**。名字数不出「搬了」还是「只是提到了」。这一把不数名字，它问一件更窄、但可机械判的事：

> **脚本一侧对某个 C 能力的处理，是不是仍然把 C 那个函数调在自己的路径上？**

量具：`python3 tools/dec_equivalence.py <ref>`（默认 `HEAD`；全部从对象库读，不检出）。同一棵树上的四个读数：

| 读数 | 含义 |
|---|---|
| `recognised` | 这个 C 能力名在 `.im` 源码里作为字符串字面出现过（脚本一侧**认识这个名字**） |
| `dispatched` | `selfhost/eval.im` 的 `call_builtin` 里有一条 `if name == "..."` 分支 |
| `forwarded` | 那条分支的体里**调用了同名 builtin** —— C 还在干活，分支只负责拆参数 |
| `reimplemented` | 那条分支**没有**调用同名 builtin（结果由别的 builtin 与脚本值算出来） |

| 读数 | 树 A `322c085` | 树 B `f49a9a5` | 主干 `3b64a2c` |
|---|---|---|---|
| C 注册名（分母） | 463 | 470 | 470 |
| `recognised` | 58（12.53%） | 58（12.34%） | 58（12.34%） |
| `dispatched` | 33 | 33 | 33 |
| **`forwarded`** | **31** | **31** | **31** |
| **`reimplemented`** | **2**（`str`、`bool`） | **2** | **2** |
| 同名 `.im` 定义 | 3 | 3 | 3 |
| 其中在 `selfhost/` | **0** | **0** | **0** |
| 其中在顶层模块 | 2（`entity.im`、`verse_kernel.im`） | 2 | 2 |
| 其中在测试/脚手架 | 2 | 3 | 3 |
| **独立脚本实现（`independent`）** | **4（0.86%）** | **4（0.85%）** | **4（0.85%）** |

**这张表读完只有一句话：脚本一侧的解释器，把 33 个 C 能力名抄进了自己的分派表，其中 31 个原样转发回 C。**

⇒ 第二把尺子那行「只有 C 实现 455 / 458」在这一把下面有一个影子数：**466 / 470**（470 减 4 个独立实现）。**注意这 4 个是候选，不是结论** —— 下一节的配对测试把它们逐个验了一遍，0 个通过。两个百分比几乎一样（99.34% 与 99.15%），但它们不是同一件事：
- 第二把把 3 个**同名定义**当成「脚本有实现」，而那 3 个里 **0 个在 `selfhost/`**、2 个在顶层模块、其余在测试与脚手架；
- 这一把把那 3 个拆开，并额外抓出 31 个**看起来像实现、实际是转发**的分派分支 —— 那是三把尺子都看不见的形状。

复跑（两行，同一棵树两个数必须相等）：

```
cd /home/sakiko/inimerse && python3 tools/dec_equivalence.py 3b64a2c
cd /home/sakiko/inimerse && python3 tools/dec_equivalence.py 322c085
```

## 第五把尺子：把同一组输入同时喂给两边（这一把才能判「搬完没搬完」）

第四把尺子把「同名」换成「C 还在不在路径上」，但它仍然只是把候选挑出来 —— `independent` 那 4 个**一个都没被验证过**。这一把把最后那一格做完：同一组输入，两边都跑一遍。

量具：`python3 tools/dec_paired_probe.py`（默认读 `HEAD` 的对象库、跑 `build/inimerse`；`--ref` / `--interp` 可换）。它对每对同名定义给出四种判定之一：

| 判定 | 含义 |
|---|---|
| `differs-today` | 脚本那一份**今天根本加载不了**，所以「等价」还不是一个可以问的问题 |
| `differs` | 做**最小**语法修复后，两边在矩阵上仍有格子不一致 |
| `agrees` | 做同样修复后，矩阵上逐格一致（是证据，不是证明） |
| `collision` | 两边只是**同名**：arity 与定义域都不同，算成「同一能力的两种实现」是错的 |

实测（`04d3141`，18 格：`nil`／`true`／`false`／0／1／−1／0.0／1.5／空串／`"a"`／空数组／`[1,2]`／`["a","b"]`／`[[1],2]`／空字典／`{"a":1}`／`{"a":[1,"b"]}`／`{"k":{"n":nil}}`）：

| 同名对 | 判定 | 实测 |
|---|---|---|
| `str` ↔ `to_str`（`selfhost/eval.im`） | `differs-today` → `differs` | 原样：`Error: expected 'expression', but got 'type'`（`eval.im` 里仍写着 `type(v)`，今天的语法是 `v.type`）；最小修复后 **16/18 相同、2 格不同**：`nil` → C 给 `nil`、脚本给 `?`；`{"k":{"n":nil}}` → C 给 `{k: {n: nil}}`、脚本给 `{k: {n: ?}}`（同一个根因：`nil.type` 取不到 `"nil"`，整个 `if tp == ...` 链一条也不中） |
| `bool` ↔ `truthy`（`selfhost/eval.im`） | `differs-today` → `agrees` | 原样同样加载不了；修复后 **18/18 相同**（`nil`/`false`/0/0.0/空串/空数组/空字典 皆 `false`） |
| `entity_get`（C ↔ `entity.im`） | `collision` | 同一份输入 `<dict>,"a"`：C 返回 **`nil`**（它要的是实体句柄 + `x/y/vx/vy/hp/kind` 六个字段名），脚本返回 **`1`**（它在字典上走 `__base__` 原型链） |
| `entity_set`（C ↔ `entity.im`） | `collision` | 同一份输入：C 返回 **`0`** 且不碰字典；脚本返回 **`5`** 并把 `d["a"]` 改成 5 |

⇒ **第四把尺子的 `independent = 4` 在配对测试下一个都不剩**：2 个是同名异义（不是同一操作，不能当实现），另外 2 个在今天的引擎里连加载都不成立，其中一个修好语法后仍在 `nil` 上不一致。把这一格写清楚之后，那句话只能这样报：

> **今天能算作「脚本侧独立实现」的 C 能力：0 个确认；1 个在 18 格矩阵上与 C 一致（`bool`）；1 个差一格（`str`）；2 个只是同名（`entity_get`／`entity_set`）。**

复跑（两行）：

```
cd /home/sakiko/inimerse && python3 tools/dec_paired_probe.py
```

## 这三个百分比是被「定义」支配的，不是被「代码」支配的（第四把尺子的四个数同理：换树只动分母 463→470，四个分子一个都没动）

同一把尺子，换一个**成员集合的定义**（不换单位），读数会移动很多；而换一棵**树**，读数几乎不动。我把两件事的跨度都量了出来：

| 尺子（单位固定） | 换定义移动了 | 换树移动了 | 比值 |
|---|---|---|---|
| 体量（文件数） | 8.41 个百分点 | 0.25 个百分点 | 33.8 |
| **体量（字节）** | 0.75 个百分点 | 0.31 个百分点 | **2.4** ← 最低 |
| 体量（行数） | 1.07 个百分点 | 0.17 个百分点 | 6.2 |
| 能力 | 82.31 个百分点 | 0.60 个百分点 | 137.6 |
| 调用链 | 29.51 个百分点 | 2.08 个百分点 | 14.2 |

**五格全部大于 1。最不敏感的那一格（体量 · 字节）也仍然被定义支配 2.4 倍。**

## 结论

**这个仓里今天没有一把尺子能证明去C化在推进** —— 最不敏感的那把（体量 · 字节）也仍被定义支配 2.4 倍，而它量的那个东西（字节）在最近这一步里只动了 0.31 个百分点。

**注意强度**：上一轮的算法把三种不同的单位当成了三个定义，给出的最低比值是 14.2 倍；只允许「同一单位、只换成员集合」之后，最低是 2.4 倍。**同一个结论，两个强度 —— 引用它的时候要连着强度一起引用。**

## 什么会让这个答案变

**下面三条都是可测量的。满足任意一条，上面那句结论就被推翻。**

1. **脚本一侧开始出现与 C 注册名同名、且语义等价的顶层定义。** 今天 451 个 C 注册名里只有 3 个在脚本一侧有同名定义（0.66%），而且两棵树之间这个数是 3 对 3 —— **一个都没动**。如果它涨到三十个量级，能力那把尺子的读数会掉到 93% 以下，**而它的「换树移动量」会第一次变成一个正数**（今天只有 0.01 个百分点）。

2. **C 一侧停止增加能力。** 今天两棵树之间 C 多注册了 7 个、脚本侧新定义 0 个。**如果某两个相邻的主干之间这个差 ≤ 0**，那么「差距在扩大」这句话当场被推翻 —— 这一条不需要任何新工具，只要再量一次那两行。

3. **出现一条「同名」之外的、可执行的等价判据。（已发生两半：第四把尺子判「C 还在不在路径上」（33 个分派里 31 个仍在转发），第五把尺子把同一组输入喂给两边（4 个候选里 0 个确认、1 个矩阵内一致、1 个差一格、2 个只是同名）。这一条现在不是缺口，是一个已经跑过的判据 —— 它的答案对「差距在缩小」不利。）** 原文如下： 今天「搬没搬」只能靠名字相同，而两个命名空间用的是两套命名习惯，所以那个判据几乎恒假 —— 这把尺子的分母因此是命名习惯给的，不是实现给的。**如果仓里出现一条能判定「脚本一侧那一段与 C 一侧那个能力等价」的检查**（例如同一组用例在两个实现上都跑通），那么比值会第一次有机会掉到 1 以下。**这是三条里唯一一条需要新东西的。**

## 这份文档的边界

- 它量的是**名字与体量**，不是**语义**。「脚本一侧有一行同名定义」不等于「那件事真的搬过去了」。
- 体量那把尺子按**文件后缀**分类。**把一批 C 文件原样改名成脚本后缀，就能让它移动** —— 我做过这个对照，它确实被骗了。
- 「能力」那把尺子的分母是**注册表里的名字**。用别的注册方式登记的能力它看不见；同名但语义不同的能力它看不出来。
- 调用链那把尺子**只跟一层**，不跟传递闭包；而且它的入口集合是「在构建脚本与测试目录的文本里被提到过」的脚本文件 —— **这是一个由文本搜索定的集合，它的漏项是静默的。**
- 第四把尺子判的是「**C 那个函数还在不在脚本那条路径上**」，**不是「两边算出来的东西一样」**。一条不调用同名 builtin 的分支，可能只是调了另一个名字的 builtin —— 那仍然要 C。「搬到脚本一侧」的最后一格（同一组用例在两个实现上都跑通）它**给不了**，所以 `independent` 只能当**上界**读，不能当「搬完了几个」读。

## 自举阶梯：把「尺子」换成「台阶」

上面五把尺子回答「搬了多少」。这一节回答另一个问题，而且它是可执行的：**脚本一侧今天到底能不能跑这门语言**。「能跑」不是一个是非题，是四级台阶，每一级都有当场能跑的命令与读数。

| 级 | 说法 | 命令 | 今天的读数 |
|---|---|---|---|
| 0 | 16 个 `selfhost/*.im` 都能被引擎加载 | `for f in selfhost/*.im; do ./build/inimerse "$f" >/dev/null 2>&1 || echo "FAIL $f"; done` | 16/16 无一 FAIL（`selfhost/eval.im` 的两处 `type(v)` 已改成 `v.type`） |
| 1 | 自举解释器能真正跑一个程序 | `./build/inimerse selfhost/twofib15.im` | `fib15=610`，退出码 0 |
| 2 | 自举编译器编译出来的程序与 C 前端跑同一个文件同结果 | `python3 tools/dec_corpus_probe.py` | `dec-corpus: files=30 same=30 differ=0 skipped=3` |
| 3 | 编译器编译**它自己**并得到同一份字节码 | 还没有 | 未做 |

第 1 级先撞上的是一个 VM 缺陷，不是脚本缺陷：`vm_array_new()` 用 `realloc` 扩张 `arrays_big` 时把 `ArrayObj` 结构体按字节搬走，而小数组的元素就存在结构体自己的 `inline_buf` 里（`a->items = a->inline_buf`），于是被搬动的每个小数组都指向已释放的旧块。release 分配器不马上回收页，所以它不表现为启动即崩，而表现为**崩点随调用次数漂移**（实测 1260 次调用正常、1280 次崩；RSS 全程恒定 71 MB）。

第 2 级的原始读数是 **26/33 同、7 异**，而这 7 个里有 5 个是同一个原因：**被编译程序的相对路径按 `compiler.im` 所在目录解析，而不是按目标文件所在目录解析**。同一条 `read_file("tests/prog1num.im")`，C 前端印 `len=0`（它的基准是脚本所在的 `selfhost/tests/`），编译后执行印 `len=15`（基准是 `selfhost/`）。修法在编译期：`compiler.im` 记住 `dir_of(tgt)`，对 `read_file`/`write_file`/`list_dir`/`mkdir`/`run_file` 的**常量**路径参数按目标目录重基。修完 26→31；剩下 3 个按名字显式跳过，三条理由都不是编译器的：`broadcast_test.im`、`cat_game.im` 开头是 `stage 600, 400`，属于 C 前端走 GUI 管线的那套 stage DSL —— 它没有字节码形态，比较的不是回归而是一个还没实现的特性；`hw_test.im` 里有一句真 `http_get("http://example.com")`，**同一个二进制连跑两次内容就不同**（字节数相同、内容不同），拿两次运行比它量的是网络。

边界：第 2 级比的是**同一份源码在两个前端下的运行结果**，不是「两个前端在语义上等价」。它只覆盖 `selfhost/tests/` 这 30 个程序，超出这个语料库的语法今天没有读数。第 3 级（自编译定点）比第 2 级强得多：它要求编译器把自己编译一遍、且编译出来的编译器还能编译同一个程序，今天这一级**一次都没跑过**。
