## 3. 规范：`type` 用集合定义

**R1（唯一性）** 语言里没有「原语类型」。类型名是**集合表达式的规范名**，唯一形式是：

```
type NAME = <集合表达式>
```

集合表达式由内置集合（`Z` `N` `Z+` `Z-` `R` `Str` `Bool` `Any` `Empty`）、区间、有限枚举、谓词，以及 `+`（并）`*`（交）`-`（差）构成。`type` **不引入新的运行时值**（沿用 ROADMAP_3.1 §范围），展开与诊断保留别名名。

**R2（`Z` 是数学整数集，不是 `int64`）** `Z` 表示全体整数，**无范围上界**。`int`、`int32`、`int64` **都不是原语**，它们是 `Z` 的有界子集：

| 日常名 | 规范定义（唯一真值） | 基数上界 | 派生表示 |
| --- | --- | --- | --- |
| `u8` / `byte` | `N * [0, 2^8)` | 2^8 | 1 字节 |
| `i8` | `Z * [-2^7, 2^7)` | 2^8 | 1 字节 |
| `i16` | `Z * [-2^15, 2^15)` | 2^16 | 2 字节 |
| `i32` / `int32` | `Z * [-2^31, 2^31)` | 2^32 | 4 字节 |
| `u32` | `N * [0, 2^32)` | 2^32 | 4 字节 |
| `i64` / `int64` / `int`（历史名） | `Z * [-2^63, 2^63)` | 2^64 | 8 字节 |
| `Z` | 全部整数 | ∞ | 立即数 + 溢出切堆大整数 |

表里的「日常名」**只是一个别名**，其定义必须由一条 `type` 给出；别名之间不构成类型层级，**唯一的关系是集合的包含关系**。

**R3（位宽是派生的，不是类型的属性）** 「这个 `int` 是 32 位还是 64 位」在语言里**没有对象**——问的是「某个具名集合的基数／范围是多少」。表示宽度由集合在编译期派生。`@bits(n)` / `@bytes(n)` 是显式钉住**并要求编译期校验**的写法（`i.json#779`：`hp: N * [0~999] @bits(16)`；「编译器自动验证位宽是否足够存储集合的所有值」）。**位置已裁定为后置**（§3.4）——紧贴集合表达式写在后面。

**R4（范围收窄是优化的合法依据，不是正确性的依据）** `Z * [0~255]` 可收窄为 u8；**无法证明范围时保持符号表示并插入可定位的运行时检查**，不静默放宽（`i.json#402`）。静态证明失败必须产生可定位的检查（ROADMAP_3.1 §验收 3）。

**R5（固定宽度只许出现在 ABI／序列化边界）** `i64`/`u8` 这类名字**只在跨语言与线上格式边界出现**，且必须由一条 `type` 定义给出，理由直接来自 `i.json#348` 自列的代价那一行。语言内部不出现宽度。

**R6（溢出策略与集合一致）** 越出集合即报错，**不回绕、不静默**。当前实现已经是这个方向（`src/vm/vm.c:3134`／`:3239`／`:3276`／`:3301`／`:3344` 五处 `vm_throw_kind(vm, "numeric_overflow")`），**但上界是 int64**（`src/vm/vm.h:42` `union { long long ival; double fval; };`）——所以今天 `x be Z = 2 ** 200` 会按 int64 溢出报错，而不是按 `Z` 的数学定义成功。R2 要改的就是这一条。

### 3.2 运算与基数记法

**已裁定（2026-10，人类指令）**：集合运算**用四则运算符**，不采用数学符号。

| 运算 | 规范记法 | `i.json#322` 的另一种记法 |
| --- | --- | --- |
| 并集 | `+` | `∪` |
| 交集 | `*` | `∩` |
| 差集 | `-` | `\` |

### 3.3 谓词可判定边界（已裁定）

**已裁定（2026-10，人类指令）**：核心支持的谓词限于**简单计算**与**正则表达式**；**常用集合库／SMT 求解器（Z3、CVC5 等）与形式化验证工具不进核心，作为拓展库接入**。

由此产生四条约束：

1. **核心必须自足**。「简单计算」= `= ≠ < ≤ > ≥` 与 `+ - * / %` 在整数／有理数上的组合，外加 `in` 成员与子集；「正则」= `Str` 上的匹配谓词。不落在这两类的谓词**不得出现在核心的 `type` 里**。
2. **降级路径保留**：判定不了就插入可定位的运行时检查（这是 R4）。`i.json#767` 的「超时 → 降级为运行时检查」与之一致，区别只是求解器从核心移到了库。
3. **内置已证结论表留在核心**（`i.json#767`：`Z+ in N`、`N in Z`、`Z in R`、`Z+ in Z`、`Z- in Z`、`Dec(n) in Q`、`Q in R`、`[a~b] in Z`、`[a,b] in R`、`[a~b] in [c~d] ↔ a >= c and b <= d`、`{1,2,3} in Z`）——它是「简单计算」的查表捷径，**不是求解器**。**表优先于库，库只能加不能改表。**
4. **拓展库的入口只有既有的 `import`**（`src/parser/parser.c:1619`），核心不依赖任何求解器；缺库时**行为不降级**（只是少了额外的证明能力，运行时检查照旧）。

### 3.4 `@bits(n)`／`@bytes(n)` 的位置：后置（已裁定）

**已裁定（2026-10，人类选择 A）**：布局注解写在类型表达式**后面**，即 `i.json#779` 的原样：

```im
hp: N * [0~999] @bits(16)
state: {"alive", "dead", "respawning"} @bits(2)
```

理由：`@bits` 是紧贴集合表达式的**布局修饰**（R3 的位宽钉住），与 `@frozen`／`@owned` 那类**声明标签**不同类，因此不受 `#721`「所有标签只出现在声明最前面」的约束。R3 的写法不变；若将来 `#721` 的前置规则也主张管到布局注解，**以本条为准**。

### 3.5 谓词集合的语法：复用 `|`（已裁定）

**已裁定（2026-10，人类选择 A）**：

```im
positive = {x in Z | x > 0}
```

`|` 就是 `case` 模式守卫用的那个 `TOK_PIPE`，挂载点复用 `src/parser/ast.h:25` 的 `Expr *guard;`。这不是妥协而是自洽：`case` 的守卫与集合的谓词**同为「过滤条件」**，共用一个符号；两者处在不同的文法位置（`src/parser/parser.c:1071-1082` 是 `case` 分支，集合构造子是 `src/parser/parser.c:516-537` 那一族），不产生歧义。

### 3.6 `Z` 的 BigInt 主干（已裁定）

**已裁定（2026-10，人类选择 A）**：**立即数 + 溢出切堆对象**。

| 面 | 裁定 |
| --- | --- |
| 表示 | 小整数走立即数快速路径；超出立即数才**切到堆上的大整数对象** |
| GC | 堆对象复用现有的引用语义（与字符串对象同一套可达性规则），**不引入**写屏障或分代处理的特殊形态 |
| ABI | 跨语言与序列化边界**不出现**未由一条 `type` 定义的宽度（R5）；需要定宽时由 `type` 显式给出并在边界转换 |
| 序列化 | 沿用既有编码 + **长度前缀**；大整数按变长字节串写出，读回时按集合约束校验（不合法即报错，符合 R6） |

这条把 R2 从「语义承诺」变成「**有表示的**承诺」：`Z` 的无界是**真的**（「只做到定宽 128/256 位」那个选项已被否），代价是 GC／ABI／序列化三处都要按上表定死。§7.3 据此结案。

### 3.7 R2 的输入语法：字面量溢出即切堆（已裁定）

**已裁定（2026-10，人类选择 A）**：**不新增任何运算符**。超过 `int64` 的整数由**字面量**直接产生——词法／解析阶段发现字面量超出 `int64` 时**直接构造堆上的大整数对象**，而不是报溢出。它与 §3.6 的运行期算术溢出切堆是**同一条表示的两个入口**。

| 入口 | 例子 | 本裁定 |
| --- | --- | --- |
| 字面量超出 `int64` | `x: Z = 123456789012345678901234567890` | **成功**（构造堆大整数） |
| 算术溢出 | `x: Z = 1` 之后反复 `x = x * 2` | 成功（§3.6 的溢出切换） |

**被否的候选**：新增幂运算符 `^`（`^` 今天连 token 都没有，且与集合运算 `*` 在视觉上混淆）；新增 `pow(a,b)` 内建（等于新立一个名字，还要定返回集合与负指数语义）；只允许由库产生（会让「`Z` 无界」的进树回归无法写成一行）。

**注意**：`2 ** 200` **依然不是合法语法**（§4.3 已撤回那个样例）；`i.json` 里指数一律以 `^` 写在散文里（`2^18`、`10^9`），**不是语言运算符**。这条裁定不改变这一点——它只是指出**不需要**运算符也能造出大数。

### 3.8 元属性 `.range` 与 `.declared` 答的是两个不同的问题（2026-10 T2 裁定）

一个值可以问两个问题，而**写法不该是答案的一部分**：

| 写法 | 答什么 | 例（`type Byte = [0~255]` / `x: Byte = 42` / `arr = [x]` / `func id(a) { return a }`） |
| --- | --- | --- |
| `.range` | **这个值**属于哪个集合，与写法无关 | `x.range` = `arr[0].range` = `id(x).range` = `set(Z interval)`；`3.7` 那种 ⇒ `set(R interval)`；对象本身就是集合 ⇒ 它自己 |
| `.declared` | **这个名字被声明成什么**；对象不是裸标识符 ⇒ `nil` | `x.declared` = 声明时那个 `Byte`；`y.declared`（只有赋值、没有声明）= `nil`；`arr[0].declared` = `id(x).declared` = `nil` |

**T2 之前 `.range` 答的是哪一个，取决于对象是怎么写的**：裸标识符答**声明**集合，其它表达式答**推断**集合。于是上例里 `x.range` 是 `Byte`（`300 in x.range` 为假）而 `arr[0].range` 是 `Z`（`300 in arr[0].range` 为真）——**同一棵树、同一个值 42、两个答案，谁都没读错**。

`.declared` 对写法的依赖**是刻意的**：声明是**名字**的属性，不是值的属性，所以只有对象写成裸标识符时才答得出来。两个名字都进了 `src/compiler/compiler.c` 的元属性表，因此对**任何**对象都安全——不会掉进「点号全局」那条路，也不会掉进下面边界 2 那条路。

**红色对照的宾语是树，不是值**：`vtest/xrange_t2_v06.im`（CTest `xrange_t2_runtime`）钉的是「两条路必须同答」；在 T2 之前那棵树上两条路不同答，该测试失败。**「它们答同一个值」是这一改的结论，不是对照的前提**——一个以自己要证明的那件事为前提的对照，是同义反复。

**两处诚实边界**：

1. **区间字面量集合的渲染**：`str(Byte)` 出来是 `set(R interval)`。判定与包含关系都是对的（`42 in Byte` 为真、`300 in Byte` 为假、`x = 300` 抛 `type_mismatch`），错的只是**显示**。另案。
2. **非裸标识符对象 + 非元属性成员名**（`arr[0].bogus`、`f().bogus`）：`EXPR_MEMBER` 落到 `src/compiler/compiler.c` 的 `return -1`，而调用方把 `-1` 当寄存器号用 ⇒ `say str(arr[0].bogus)` **段错误（RC=139）**，写成裸语句则被静默丢弃（RC=0，什么也不说）。**nil 安全的 `?.` 一直是实现的**（降为 `OP_INDEX_GET`）⇒ 这是**缺一条 lowering**，不是设计取舍。T2 这一笔把它变成干净报错（`Error: '.bogus' on something that is not a name is not implemented`，RC=1，与只读属性错误同一条出口）；红色对照 `vtest/member_on_nonname_v06.im`（CTest `member_on_nonname_runtime`），**在 CTest 层量过**：修前 `***Exception: SegFault`，修后 `Passed`。**`.bogus` 最终该报错、还是该降成与 `?.` 同体只差 nil 守卫的 `OP_INDEX_GET`，仍未裁定**——登记在 §7.8 第 5 条。
