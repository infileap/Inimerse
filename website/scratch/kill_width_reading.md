## 二、★★★ 头条：加上左边界之后，`:87` **仍然不被收** —— 而且收它的不是 `!D`

### 2.1 「加上词边界」在今天的源码上是一个 no-op

源码逐字（`website/scratch/ruler_gui6.js:111`）：

```js
new RegExp('!' + n + '\\b'), new RegExp('\\b' + n + '\\s*!=\\s*null'), new RegExp('\\b' + n + '\\s*===\\s*undefined'),
```

**它本来就带 `\b`。** `\b` 给的是**右**边界，而出问题的是**左**边 —— `!D` 在 `!!D.statuses[…]` 里是**第二个感叹号**接上 `D`。
三种变体对 `:87` 那条语句**真实文本**的结果（`website/scratch/kill_boundary_probe.js`）：

```
V0 原样 `!D\b`（= 今天源码）              ⇒ isKill = true
V1 加左边界 `(?:^|[^!\w])!D\b`           ⇒ isKill = false   ← 有效形态
V3 无边界 `!D`                           ⇒ isKill = true    ← 右边界不是关键
```

⇒ **判据 1 成立：一条修法如果只写「加边界」而不写是哪一边，它在源码上可能已经满足 —— 于是「我改过了」与「我没改」在读数上同形。**

### 2.3 ★★★ 收 `:87` 的是**另一条** kill 规则 —— 逐字是 `:68` 那条语句上的 `\bD\s*&&`

**这是派件那个 ★ 的答案。** 轨迹（`.build/` 里的插桩副本，逐字）：

```
TRACE website/scratch/check_citations.js:87  tainted(D)=true  defLine(D)=44
  stmt=87-97  idx=30  isKill=false
  back idx=22 lines=68-68 isKill=true isDef=false :: "check('有 entries 且非空', !!(D && Array.isArray(D.entries) && D.entries.length), D "
  back idx=21 lines=67-67 isKill=true isDef=false :: "check('有 ref', !!(D && D.ref), D && D.ref);"
  back idx=16 lines=44-44 isKill=false isDef=true :: "const D = sandbox.window.INFIVERSE_DECISIONS;"
```

`:87` 那条语句自己的 `isKill` **已经是 false**（左边界修好了），但**回溯走法**往后退到 **`stmt 68`** 时撞到 **`isKill = true`** ⇒ `protectedBy = 68` ⇒ 不报。

⇒ ★★★ **判据（署我名）：把「判空」放在【语句】粒度上、再用【线性回溯】把保护向后继承，会让前面任何一条语句上的 `&&` 保护后面所有语句 —— 于是 `:87` 的保护不是它自己的，是 `:68` 的。**
⇒ **按派件要求照实说：加上左边界之后 `:87` 仍然不被收 ✓；那时收它的是【另一条】kill 规则（`check_citations.js:68` 那条语句上的 `\bD\s*&&`，经线性回溯继承）。不许把它归回 `!D` 这一条。**

### 2.4 ★★★ 我自己在 2.3 之前问错了问题

我做过一个 `V2` 探针：把 `!D` 这一条**整条删掉**，对 `:87` 那条语句的**文本**逐条试剩下的 kill 模式，得到 **0 条命中** ⇒ 结论「只有 `!D` 这一条在收它」。
**这个结论是错的**，而 2.3 的轨迹给了真相。

⇒ ★★★ **判据（署我名）：一张 kill 表上 0 条命中，与一条回溯走法上「撞到了别处的 kill」是两个不同的命题。用前者回答后者，会得到「只有这一条在收它」，而真相是这一条根本不是收它的那一条。**
⇒ 这正是本会话反复出现的那一族：**我把问题问在了错误的层上，而两层的输出都自洽。**
